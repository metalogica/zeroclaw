## 1. Authority

This doctrine governs `@soulbound-labs/praxis` — the durable task tracker installed into every ZeroClaw agent runtime. Praxis is a CLI consumed by the agent via shell tool, distinct from delegated specialist agents and from in-process domain logic.

This doctrine covers:

- The cognitive contract for what makes something a bead (three load-bearing properties; worth-being-a-bead filter)
- The two-repo publish/consume boundary
- Versioning policy (semver-immutable, build-time pinned)
- Storage contract (`/zeroclaw-data/workspace/.praxis/`), including the worktree topology and self-healing projection direction
- Producer-side auto-sync semantics (command-boundary commit, agent-surface minimalism)
- Operational runbook for bumping praxis in production
- Forbidden patterns specific to praxis (publishing, consuming, runtime)

This doctrine **defers** to:

- `infra/infra-doctrine.md` §15.23 — for publish-workflow rules (tag-driven, GitHub Packages, gate sequence). All publish-side details live there.
- `claw-doctrine.md` §5.7 — for agent-side capability framing (memory / web search / Praxis triad).
- `claw-doctrine.md` §17.1, §17.4 — for `claw-workspace.ts:renderToolsTemplate` consumption of `praxis-commands.ts`.
- `web-app/domain-doctrine.md` §3.1 — for `praxis-commands.ts` directory placement.
- `packages/praxis/README.md` — for the consumer's hands-on install pattern (workstation, Dockerfile, fork CI).

If you find yourself documenting *how* to publish or *what* a publish workflow looks like, you're in the wrong file. That belongs in `infra/infra-doctrine.md` §15.23.

## 2. Bead Semantics

This section defines **what makes something worth being a bead**. §5 (Storage Contract) and §6 (Agent-Facing Surface) define the *mechanics* — where bead files live, how they're persisted, the lifecycle commands that act on them. Those rules are silent on the prior question: when an agent has a candidate piece of state, should it become a bead at all, or does it belong in a different primitive entirely?

The mechanics doctrine is stable. The semantic-typing doctrine (next-action / project / reference / someday, etc.) sits *above* this section and evolves separately (§2.3). This section codifies only what is invariant across all uses of praxis — the contract every bead, regardless of type, MUST satisfy.

### 2.1 The three load-bearing properties

A bead is a **persisted, addressable, state-tracked unit of work**. All three properties are MUST. If any one is missing, the candidate is not bead-shaped and belongs in a different primitive.

| Property | Definition | Failure mode if missing |
|---|---|---|
| **Persisted** | Survives across sessions and context compaction. Stored to disk on the `praxis-sync` worktree branch at `.praxis/data-sync/issues/<id>.md` (§5.3 topology). | The state evaporates with the conversation; future-session agents have no record. |
| **Addressable** | Has a stable identity (`<id>.md`) that other things — other beads, specs, future-session agents, audits — can reference. | No reference target; dependencies, projection mirrors, and cross-bead links collapse. |
| **State-tracked** | Has at least one intermediate state between "doesn't exist" and "fully done." The bead lifecycle (open → in-progress → blocked → closed → reopened → atticked) provides this. | Binary lifecycles ("do it; it's done") don't need bead machinery. Just do the thing. |

**Property × primitive matrix.** When the candidate satisfies only some of the three properties, the doctrine pushes it to a different primitive:

| Persisted | Addressable | State-tracked | → Right primitive |
|:---:|:---:|:---:|---|
| ✅ | ✅ | ✅ | **bead** |
| ✅ | ✅ | ❌ | markdown doc (guideline, spec, doctrine) |
| ✅ | ❌ | ❌ | notes / scratch file |
| ❌ | — | — | ephemeral conversation context |

### 2.2 The worth-being-a-bead filter

At `praxis create` time, the agent MUST apply a three-question filter before promoting a candidate to a bead. Each question maps directly to one of the §2.1 properties:

1. **Compaction-loss test (persistence).** *Does losing this on context compaction matter?* If no, it belongs in conversation. If yes, it needs persistence — bead or markdown doc.
2. **Reference test (addressability).** *Will anything later — other beads, specs, follow-up sessions, audits — need to reference this by stable identity?* If no, a scratch file or doc suffices. If yes, addressability is required.
3. **State test (state-tracking).** *Are there meaningful intermediate states (in-progress, blocked, awaiting review, archived) the agent will move through?* If no, it's a one-shot — just do it. If yes, bead machinery is the right fit.

All three pass → bead. Partial pass → use the §2.1 matrix to pick the right primitive.

The filter is a **rejection test**, not a recommendation engine. When in doubt, the bias is *not* to create a bead. Bead-shaped state earns the cost of the persistence/addressability/projection chain; non-bead state should not pay it.

### 2.3 Layering — semantic types live above this section

Beads have **types**. A bead may be a *next-action* (atomic, executable, doable-right-now), a *project* (an outcome that decomposes into other beads), *reference* material (something the agent reads but never executes), or any other semantic flavor a workflow needs. These types are real, useful, and worth doctrine — but they belong in a **separate fragment**, not this one.

Rationale: the mechanics contract (§2.1, §2.2) is invariant across all praxis usage and across all semantic-type vocabularies. The semantic-type vocabulary itself is free to evolve — GTD framings today, possibly different framings tomorrow as workflow patterns mature. Cramming the evolving semantic layer into the mechanics doctrine would couple a stable contract to an experimental vocabulary and prevent both from doing their job.

This section codifies only:

- A bead MUST satisfy §2.1's three properties (regardless of type).
- An agent MUST apply §2.2's filter at `praxis create` time (regardless of intended type).

The semantic-type doctrine, when it lands, sits above this section and refines *what flavor* a bead is — not *whether* it is a bead.

**Role axis (v1.10.0).** Beads carry an orthogonal **role** alongside their `type` (bead-kind) and `writer` (authoring pipeline). The role names *which authorial channel produced the bead*, not what kind of work the bead represents. `BEAD_ROLES` is an **open enumeration of permanent literals** (NOT transitional; per methodology §3) — values added here are never removed and never repurposed. v1 literals:

| Role | Producer | Storage signal |
|---|---|---|
| `prior_work` | Validation pipeline (§9) — `internal.specValidation.upsertPriorWorkBead` writes `writer: "validation"` + `role: "prior_work"`. | `validationFingerprint` on the bead row. |
| `execution` | Execution runtime (§10) — `praxis spec activate-execution` materializes beads with `metadata.execution_id` set. The projection emitter derives `role: "execution"` from that metadata; the consumer (`writer: "workspace"`) stamps the row. | `metadata.execution_id` on the bead row. |
| `undefined` (no role) | Workspace projection — `praxis create` and other workspace verbs write beads without an `execution_id`; the projection emits no `role` field. | absence of `execution_id` AND absence of `validationFingerprint`. |

Role is a workflow-discriminator, not a typing axis — the type system pins the value set, while the workflow doctrine that defines each role's mechanics lives in the appropriate section (§9 for `prior_work`; §10 for `execution`).

## 3. Two-Repo Boundary

Praxis lives at a precise boundary:

```
soulbound-labs/clawcraft (this monorepo)
  packages/praxis/                 — source of @soulbound-labs/praxis
  apps/clawcraft/domain/           — in-repo *consumer* (renders the agent-facing
                                     verb catalog into AGENTS.md from the manifest
                                     snapshot; PRAXIS_AGENT_COMMANDS now only feeds
                                     TOOLS.md usage-prose literals — §6.5)
  apps/clawcraft/convex/           — does NOT import praxis source or runtime

soulbound-labs/zeroclaw (sibling fork repo)
  Dockerfile (Wolfi `release`)     — installs @soulbound-labs/praxis@<pin> from
                                     GitHub Packages at image-build time. Binary at
                                     /opt/praxis/, symlink at /usr/local/bin/praxis.

ZeroClaw runtime image (production)
  Pod runs the agent. Agent invokes `praxis <subcommand>` via shell tool.
  Storage: /zeroclaw-data/workspace/.praxis/ on PVC.
```

### 3.1 Rules

- **MUST NOT** depend on the `./cli` subpath of `@soulbound-labs/praxis` from any clawcraft `package.json` or any clawcraft source file. The CLI subpath carries the I/O shell (commander, simple-git, atomically, node:fs, node:child_process, HTTP projection client) and is intended only for the ZeroClaw container's binary install — pulling it into a clawcraft bundle would bloat the build, break browser/Convex-V8-isolate consumability, and re-introduce the runtime-fork-vs-build-import role confusion §3.1 was originally written to prevent.

- **MAY** depend on `@soulbound-labs/praxis` (the default subpath, which resolves to `src/core/` per §3.2) via the pnpm workspace protocol (`"@soulbound-labs/praxis": "workspace:*"`) for in-monorepo consumption of the pure domain surface — schemas (Zod), enum const tuples (`BEAD_TYPES`, `BEAD_STATES`, `BEAD_SCHEMA_VERSION`), the canonical `Bead` type, parsers, validators, factory logic. Workspace-protocol consumption resolves to `packages/praxis/dist/core.mjs` (the built `.` target), so `packages/praxis/` MUST be built before clawcraft typecheck.

- The "circular conceptual loop" the original §3.1 guarded against (clawcraft publishing what it consumes) is dissolved under workspace-protocol consumption: clawcraft is not consuming the *published* artifact in-monorepo — it is co-developing source under one git root. The published artifact is still consumed only by ZeroClaw at image-build time. ZeroClaw MUST NOT workspace-import; the registry remains the sole cross-repo channel.

- **MUST** keep cross-repo coupling one-way and explicit:
  - clawcraft → publishes a versioned artifact to GitHub Packages
  - ZeroClaw → consumes the artifact at image-build time
  - ZeroClaw image → deployed to GKE; clawcraft Convex sets `CLAW_DOCKER_IMAGE` to that image's URI

  The two repos communicate only via the registry. There is no submodule, no path import, no shared build step.

- **MUST** keep `PRAXIS_AGENT_COMMANDS` consumed only by `apps/clawcraft/domain/claw-workspace.ts` — `renderToolsTemplate` (TOOLS.md usage prose) and `renderAgentsTemplate` (AGENTS.md sop-ingestion prose), both via the module-scope `verb(...)` extractor (post-`rnk-rwfn` the constant feeds prose literals only; the verb *catalog* is the manifest snapshot — §6.5). The grep invariant — `grep -rn "praxis create" apps/clawcraft/domain/` returns exactly one location (the constant in `praxis-commands.ts`; the renderers derive the literal at runtime and hold none) — is enforced by the unit test in `apps/clawcraft/test/unit/domain/claw-workspace.test.ts`.

### 3.2 Internal core/cli boundary

The published `@soulbound-labs/praxis` package is internally partitioned into two subpaths, exposed via `package.json#exports`:

| Subpath | Source dir | Role | Importable from |
|---|---|---|---|
| `.` (default) | `packages/praxis/src/core/` | Pure domain — schemas, parsers, factory logic, validators. No fs, git, http, commander. | Any JS runtime (browser, Convex V8 isolate, future MCP server) |
| `./cli` | `packages/praxis/src/cli/` | I/O shell — commander Program, fs/git operations, HTTP projection client, terminal output. | Node only |
| `bin` (binary) | `src/cli/bin.ts` (bundled to `dist/bin.mjs`) | The `praxis` executable the agent invokes via shell tool. | Pod runtime (ZeroClaw) |

The boundary is enforced by a hard `no-restricted-imports` ESLint rule (`packages/praxis/eslint.config.js`): every file under `src/core/` is forbidden from importing `src/cli/*`, `node:fs*`, `node:child_process`, `node:net`, `node:http`, `node:https`, `node:os`, `simple-git`, `atomically`, or `commander`. CI fails on violation. `gray-matter` is permitted in core because praxis uses it as a pure string parser (`matter(string)`, never `matter.read`).

Rules:

- **MUST** keep `src/core/` node-free. The boundary is the load-bearing contract that makes future in-process consumption (Convex actions, browser bundles) possible. Adding a `node:*` import to a core module silently breaks the contract; the ESLint rule and the `tests/node-free-core.test.ts` guard are the two backstops.

- **MUST** put pure presentation primitives (const tables of icons, named-color helper TYPES) in core, not cli. The pattern in §3.2 emerged from `cli/lib/output.ts:ICONS` being needed by `core/status.ts:getStatusIcon` — the constant moved to `core/icons.ts` and `output.ts` re-exports it. CLI consumers see no change; core gains a pure import path. Apply the same pattern for any future presentation primitive that has no I/O footprint.

- **MUST** preserve published-artifact symmetry. The `./cli` subpath is intended only for the ZeroClaw container's binary install. The schema-mirror retirement brief (`docs/tasks/ongoing/praxis-schema-mirror-retirement/`, 2026-05-17) wired the first workspace-protocol consumer. Future briefs may follow the same pattern.

- **First in-monorepo consumer landed 2026-05-17.** `apps/clawcraft/domain/praxis-beads.ts` is the first clawcraft module to import from `@soulbound-labs/praxis` (default `/core` subpath) via workspace protocol. If a second consumer of the camelCase value-object surface emerges, the translator may move to `packages/praxis/src/core/` at that point — not before. Moving it ahead of a second consumer would be dormant scaffolding (§8).

- **MUST NOT** ship dormant scaffolding in core. The internal partition is structural infrastructure; new core modules (e.g., port interfaces for the future validation pipeline) land WITH their first consumer, not ahead of it (§8 dormant-scaffolding pattern).

## 4. Versioning Model

### 4.1 Semver-immutable

Every published version is permanent. The publish workflow refuses to re-publish an existing version (see `infra/infra-doctrine.md` §15.23 step 5.3 — pre-flight `npm view`). To "fix" a published version, cut a new patch tag.

### 4.2 Tag-driven

Releases are git tags of the form `praxis-v<semver>` on the clawcraft repo's `main` branch. The tag IS the release intent — pushing to `main` does not publish.

### 4.3 Build-time pinned in consumers

ZeroClaw's `Dockerfile` declares `ARG PRAXIS_VERSION=<semver>` and installs that exact version at image-build time.

- **MUST NOT** use floating tags, `@latest`, or semver range specifiers in any consumer's pin. The pin is the production contract.

### 4.4 Why build-time pinning is non-negotiable

1. **Pod startup must not depend on registry availability.** Registry outage → no new pods.
2. **Atomic rollback.** One image SHA = one (zeroclaw-runtime, praxis-version) tuple. Reverting `CLAW_DOCKER_IMAGE` reverts both atomically.
3. **Reproducibility.** Anyone can rebuild the same zeroclaw image and get identical praxis bits.
4. **No runtime drift.** All pods running the same image SHA have identical praxis behavior.

### 4.5 Decoupling alternatives

Three escape valves exist for decoupling praxis-bump cadence from zeroclaw-bump cadence:

| Alternative | Trade-off | Status |
|---|---|---|
| Sidecar / init container with its own praxis image | Extra container, separate publish pipeline | Not in use |
| Runtime `npm install` at pod start | Network dep at provision time, registry outages = pod-start outages | **Forbidden** (§8) |
| `COPY --from=ghcr.io/.../praxis:<v>` of a published praxis Docker image | Bumping praxis becomes a one-line `FROM` change | Not in use |

Any move to a decoupling alternative requires an explicit migration plan touching this doctrine. Not a unilateral Dockerfile edit.

### 4.6 Runtime dep bundling — bundle everything

The praxis binary runs inside a Wolfi-base ZeroClaw image that does NOT have `npm install` available at runtime. Every runtime dep MUST be bundled into the published binary via the build step (esbuild-equivalent `--bundle`).

Rule: **bundle every dep listed under `dependencies` in `packages/praxis/package.json`.** No allow-list, no ESM-vs-CJS exception, no observe-and-react pattern. The cost (slightly larger artifact, ~tens of KB per dep) is irrelevant for a binary the agent invokes via shell tool. The cost of NOT bundling (silent runtime failures discovered only when the agent hits a code path that imports the missing dep) is observable as production drift.

Reactive bundle-fix commits (the May 12 pattern of "bundle gray-matter," "bundle pretty-bytes," "bundle pretty-ms" in 2-minute succession) are an antipattern signal — they indicate a dep crossed the boundary without going through the build. The fix is correct but the trigger (runtime failure) should not be the discovery mechanism.

Build verification: `pnpm --filter @soulbound-labs/praxis exec node dist/cli/index.js --version` succeeds with zero env (no `node_modules` traversal). If that breaks after adding a dep, the bundle config needs an update before the dep is merged.

The Rust port (deferred) eliminates this concern by compiling to a single binary. Until then, "bundle everything" is the cheapest rule.

### 4.7 Dev version string — what the bake captures and when

`praxis --version` reports a baked-at-build-time identifier produced by `packages/praxis/scripts/git-version.mjs` and embedded into `dist/bin.mjs` by tsdown (`__PRAXIS_VERSION__` define). The runtime never re-derives it.

**Format:** `X.Y.Z-dev.N.hash[-dirty]`

| Segment | Meaning at bake time |
|---|---|
| `X.Y.Z` | Most recent `praxis-vX.Y.Z` tag with its patch component auto-bumped (`0.4.0` tag → `0.4.1` prefix). Stays `0.4.1` for every dev build between that tag and the next. |
| `-dev` | Pre-release marker. Consumers pinning to `0.4.0` or `0.4.1` ignore this build. |
| `.N` | `git rev-list <last-tag>..HEAD --count` at bake time. |
| `.hash` | 7-char `git rev-parse --short HEAD` at bake time. |
| `-dirty` | `git diff --quiet` returned non-zero at bake time — index or working tree had uncommitted changes. |

**The bake fires only when tsdown rebuilds.** `pnpm dev:claw:watch-praxis` (= `tsdown --watch`) re-bakes on source-file change. `git commit`, `git tag`, and `git push` do NOT trigger a rebake — they're invisible to the watcher unless they coincide with a source-file save. As a result:

- A binary whose version string says `dirty` may have already been committed cleanly. The `-dirty` is a snapshot of the working tree at the moment of the last source-triggered rebuild, not a live property.
- A binary's embedded `hash` may be older than the current HEAD if commits landed without subsequent source edits.
- **Binary code freshness ≠ version-string freshness.** The bytes can be current (latest watcher rebuild) while the embedded SHA lags behind HEAD by one or more commits.

This matters when debugging "why doesn't the container have my change?" The right diagnosis is `ls -la /opt/praxis/dist/bin.mjs` (mtime tells you when the binary last changed) — not the version string. Trust the version string only for "what HEAD was the last time tsdown rebuilt me."

In published builds (the tag-driven publish workflow, §7.2 / §15.23), the bake fires once during the CI build and the version string equals the tag (`X.Y.Z`, no `-dev` suffix, no `-dirty`). The dev-loop ambiguity is purely a local concern.

## 5. Storage Contract

Praxis stores task data at:

```
/zeroclaw-data/workspace/.praxis/
```

This is on the user-owned workspace PVC (per `claw-doctrine.md` §9.1). Implications:

- **Persistent across pod restarts.** PVC outlives pod lifecycle.
- **Visible to the user via the file manager.** The user can inspect, back up, or delete praxis state outside the agent loop.
- **Owned by the agent.** This is not a system-files path (`/system/`); it is part of the agent-owned workspace.
- **No system-level migration path.** If praxis changes its on-disk format incompatibly, every existing user's `.praxis/` directory becomes stale. Format migrations are praxis's own responsibility (see `praxis-format.ts` and the format-version field in praxis's config schema).

### 5.1 Rules

- **MUST NOT** read or write `/zeroclaw-data/workspace/.praxis/` from any clawcraft Convex query, mutation, action, or HTTP route. The directory is opaque to the control plane.

- **MUST NOT** mount or copy `.praxis/` content into the system files contract (ConfigMap-mounted at `/system/`). System files are control-plane-rendered, immutable from inside the pod, and not durable across format changes — the opposite of what praxis needs.

- **MUST** treat `.praxis/` as agent-owned for backup, retention, and lifecycle decisions. If a future GDPR-style deletion flow needs to wipe praxis state, it does so via the same workspace-deletion path used for other agent-owned files.

- **MUST** uphold the `praxisRoot === gitRoot` invariant. The praxis project root and the workspace's git root are the same directory: `/zeroclaw-data/workspace/`. `.praxis/` and `.git/` are siblings under that root. The post-commit hook installer (`praxis project install-hooks`) writes to `<gitRoot>/.git/hooks/post-commit`, and the projection chain (§6.2) assumes the hook fires from a commit whose worktree resolves under that same root (§5.3). Moving `.praxis/` into a subdirectory of a larger repo, or running praxis in a workspace without `.git/` at its root, silently breaks both bootstrap and projection. The known prod/dev asymmetry around `git init` is documented at §7.6.

### 5.2 Two parallel stores — on-disk `.praxis/` and Convex bead-mirror tables

Praxis-managed bead data exists in two places by design:

| Store | Owner | Writer | Purpose |
|---|---|---|---|
| `/zeroclaw-data/workspace/.praxis/` (PVC) | agent | `praxis` CLI inside the pod | The agent's working bead + spec memory across pod restarts. Authoritative source of truth. |
| Convex tables (`beads`, `bead_dependencies`, `bead_labels`, `commits`, `specs`, `spec_versions`, `spec_nodes`, `spec_edges`) | clawcraft control plane | see per-table writer enumeration below | UI-side bead + spec mirror, subscribable by the web app for the task panel. |

**Direction of authority for workspace beads is one-way: pod → Convex.** The pod is authoritative for every workspace-source bead. Convex is the read-side projection cache for them. The validation pipeline introduces a second, orthogonal authorial channel for `beads` only (§9); it writes findings-derived `role: "prior_work"` rows that the pod never sees.

Rules:

- **MUST** import the `BeadType` / `BeadState` / `BeadSchemaVersion` types from `@soulbound-labs/praxis` (default `/core` subpath, workspace-protocol-resolved per §3.1) using a **type-only import** (`import type { ... }`). Praxis is the single source of TYPE truth for bead enums and the canonical `Bead` shape. The type-only import is erased at compile time, so it has zero bundle cost in any consumer.

  **MUST NOT** runtime-import `BEAD_TYPES` / `BEAD_STATES` / `BEAD_SCHEMA_VERSION` (or any other value export) from `@soulbound-labs/praxis` inside any module that ends up in the Convex bundle graph (anything reachable from `convex/schema.ts`, `convex/_generated/*.ts` consumers, `convex/*.ts` actions/queries/mutations). The praxis `dist/core.mjs` artifact transitively pulls in `rolldown-runtime-*.mjs`, which has a dead `import { createRequire } from "node:module"` that rolldown injects into the shared chunk. Convex's V8-isolate-target esbuild cannot resolve `node:module` and fails the `Bundling component schemas and implementations` phase. Until that upstream defect is fixed (tracked: see bead with `originating-session: 2026-05-17` for praxis dist build), Convex-reachable modules MUST source runtime enum tuples from `apps/clawcraft/domain/praxis-beads.ts` (which declares them locally) instead.

  The module at `apps/clawcraft/domain/praxis-beads.ts` is **a translation-layer surface, not a structural mirror.** Its role is bounded:
  - **Type imports**: `BeadType` / `BeadState` from praxis core (type-only, erased at compile time).
  - **Local runtime tuples**: `BEAD_TYPES` / `BEAD_STATES` / `BEAD_SCHEMA_VERSION` declared as `as const` arrays. Re-exported to ALL clawcraft consumers (frontend, Convex schema, projection).
  - **Bidirectional type-completeness assertions**: two paired conditional types per enum (`PraxisBeadType extends BeadType ? true : never` AND `BeadType extends PraxisBeadType ? true : never`). If praxis adds a new type/state and clawcraft misses it, OR clawcraft has a phantom value praxis doesn't have, tsc fails compile at the next typecheck. This pins the runtime tuples to praxis's type-level truth without paying the Convex-bundle cost of runtime praxis import.
  - **Value-object shape** `BeadValueObject` (camelCase: `praxisId` instead of `id` to avoid Convex's reserved `_id`, `shortId`, `tickleUntil`, `decidedAt`, `expectedAt`, etc.). This shape exists for clawcraft's Convex column + frontend prop conventions; it is not part of praxis's public contract.
  - **Presentation helpers** (`groupBeadsByState`, `filterBeadsByTypes`, `selectBeadByPraxisId`, `isBeadOfType`, `BEAD_TYPE_DISPLAY_LABEL`, `BEAD_STATE_DISPLAY_LABEL`, `BEAD_STATE_DISPLAY_ORDER`) that operate on `BeadValueObject`. These stay local because they encode clawcraft UI / i18n choices, not praxis-domain truth.

  **Where the snake_case → camelCase translation actually happens:** in praxis CLI's projection emitter (the post-commit-hook → `praxis project push` chain). The producer converts snake_case `Bead` to camelCase `BeadValueObject` shape before POSTing to `/api/praxis/projection`. The Convex consumer (`applyProjection`) receives camelCase already; `isProjectionPayload` is a pure structural runtime guard, NOT a translator. clawcraft has no client-side translator function — adding one would be dormant scaffolding (§8) until a second consumer of the camelCase surface emerges.

  A `readFileSync`-based hygiene test (`apps/clawcraft/test/unit/domain/praxis-beads.test.ts`) MUST assert that `praxis-beads.ts` does not import `@soulbound-labs/praxis/cli`, `convex`, `react`, `@xyflow`, `dagre`, `zustand`, or `@clawcraft/treasury`. The praxis type-only import (`import type { ... } from "@soulbound-labs/praxis"`) is permitted. The previous enum-parity tests (retired 2026-05-17) are no longer needed — the bidirectional type-completeness assertions in `praxis-beads.ts` enforce parity at compile time.

- **MUST** use the `praxis.bead/v1` storage APIs (`readBead` / `writeBead` / `listBeads`) in every write command. The `praxis.issue/v1` APIs (`readIssue` / `writeIssue` / `listIssues`) are deprecated: they read and write a schema the structural mirror above does not recognize, so any record they touch is invisible to the projection. A command still on the issue APIs throws `Issue not found: <id>` against the `praxis.bead/v1` data that `praxis create` writes. Grep invariant: `grep -rln "readIssue\|writeIssue\|listIssues" packages/praxis/src/cli/commands/` returns zero files — this SHOULD be enforced by a unit test (today it would fail; see Known drift). **Known drift (2026-05-14):** `dep.ts` and `label.ts` are still on the issue APIs — they are wired for auto-sync (§6.1) but throw before reaching the commit boundary. Tracked as praxis bead `rnk-en7j`; until it lands, §6.1's write-command set has two non-functional members.

- **MUST NOT** read or write `.praxis/` from any Convex query, mutation, action, or HTTP route (§5.1 still binds). Convex receives the projection as a JSON payload over HTTP; it never traverses the directory.

- **MUST NOT** call Convex bead mutations directly from the praxis CLI / pod loop. The agent-facing surface is on-disk only; the projection is fired by the git `post-commit` hook (the `praxis-link` brief).

### 5.2.1 Self-healing property

The command-boundary auto-commit rule (§6.1) stages everything currently uncommitted under the worktree's `.praxis/data-sync/` — not just the files this command wrote. Practical consequence: an orphan bead or spec file left uncommitted by a prior crashed invocation gets swept into the next write command's commit. The producer→UI gap is self-healing — the next agent write closes it without operator intervention.

Future tightening of the auto-commit helper to only stage this-command's writes would silently break this property. Implementations MUST preserve the "stage everything currently uncommitted under `.praxis/data-sync/`" semantics.

Specs benefit from this property natively: per §5.2.2, spec files live in `.praxis/data-sync/specs/` under the same worktree, so a `praxis spec create` write and the worktree-commit boundary share one mechanism with beads — there is no second commit path to keep in sync. Validation rows (v1.11.0) and execution rows (v1.10.0) inherit the same property because their `validations/` and `executions/` directories sit under the identical `.praxis/data-sync/` root — a crashed or interrupted `spec verify --persist` / `spec activate-execution` invocation leaves the JSON row on disk; the next write-command sweep stages it into the next worktree commit without operator intervention.

### 5.2.2 Per-thread spec storage — owned directory, CLI-only writes

Each clawcraft chat thread owns at most one spec. Spec files live as siblings of bead files inside praxis's owned storage:

- **Path.** `<praxisRoot>/.praxis/data-sync-worktree/.praxis/data-sync/specs/<threadId>.md`, resolved via `resolveSpecsDir(praxisRoot)` in `packages/praxis/src/lib/paths.ts`. `<threadId>` is the Convex `Id<"threads">` string token, treated as opaque on the producer side.
- **Sole writer.** Praxis owns the canonical path; the agent never writes the spec file directly. Authoring goes through the `praxis spec create | update` CLI verbs, which call `writeSpec` in `packages/praxis/src/file/spec-storage.ts` (atomic temp-file + rename, refuses to write outside the specs dir).
- **Bare filename in projections.** The projection emits `<threadId>.md` (no `specs/` prefix and no `.spec.` infix); the consumer regex (`apps/clawcraft/convex/praxisLink.ts:SPEC_FILENAME_RE = /^(?<threadId>[a-z0-9]+)\.md$/i`) matches the same shape. The parent directory is implicit since storage is owned. `parseThreadIdFromSpecPath` verifies via `ctx.db.normalizeId("threads", ...)` before storing the foreign key.
- **One spec per thread, two files per thread (v1.13.6).** Each thread owns up to two sibling files: `<threadId>.md` (pure natural-language prose — Overview, Outcome, narrative rules) and `<threadId>.factory.md` (Triggers + Bead Factory YAML blocks; optional on disk; REQUIRED-by-CLI for any spec authored by `praxis spec create | update` after v0.9.0). The filename `<threadId>.md` is the natural key; the `(user, thread)` pair is unique in the `specs` table via `by_user_thread`. `praxis spec create` errors if a spec already exists for the thread; `praxis spec update` errors if none does. Both files are written by `writeSpec` in two sequential atomic writes (prose first, factory second) inside a single command boundary; the post-commit hook fires after both writes return. The factory sibling rides on the SAME `ProjectionSpecChange` row as the prose file via a REQUIRED `factoryMarkdown: string` field — it is NOT a separate change row. `parseSpecFactory` + `parseSpecTriggers` run against the factory body only; the prose body is never parsed for workflow declarations. The bare-filename projection rule (`SPEC_FILENAME_RE = /^([a-z0-9]+)\.md$/i`) is unchanged — `<threadId>.md` remains the natural key, and the regex's `[a-z0-9]+` character class safely excludes `<id>.factory.md` siblings from `listSpecs` enumeration (defensive regression test in `packages/praxis/tests/spec-storage.test.ts`).
- **Title parsing.** The projection extracts the first H1 (`^#\s+...`) from the PROSE body and stamps it on `ProjectionSpecChange.title` (then on the `specs.title` Convex column). Bodies without an H1 fall back to the threadId stem. The factory body is never scanned for an H1.

Orphan threadIds (filename parses to a valid Id shape but the thread is missing or owned by a different user) are accepted, stored, and warned — never rejected, because the thread may have been deleted between agent write and projection apply.

The historical `sweepWorkingBranchSpecFiles` / `SpecSweepResult` / `AutoSyncResult.specSweep` carriers are gone; grep invariant: zero matches in `packages/praxis/src/`.

### 5.2.4 Workflow templates — combined-doc import (`praxis.workflow-template/v1`)

A **workflow template** is a single bundled markdown document (the shape the `praxis template` subsystem stores under `packages/praxis/docs/templates/` and `--list`s) that carries BOTH halves of a per-thread spec — the natural-language prose AND the factory body (`## Triggers` + `## Bead Factory`) — separated by exactly one sentinel line `<!-- praxis:factory -->`. It is the import counterpart to the §5.2.2 two-file storage: one doc on disk, two files at create time.

- **Storage is flat.** Templates MUST live directly under `docs/templates/` (the doc-cache loader is non-recursive — `src/cli/file/doc-cache.ts:loadDirectory` reads one level). A `workflows/` subdir would ship to `dist/` but never be discovered.
- **The split is pure core.** `packages/praxis/src/core/workflow-template.ts:splitWorkflowTemplate(combined) → { proseBody, factoryBody }` is node-free (§3.2). It is deterministic — exactly one delimiter; everything before it is prose, everything after is factory — and fails fast (`WorkflowTemplateError`) on a missing/duplicate delimiter, an empty half, or a factory half lacking `## Triggers`/`## Bead Factory` (the §6.1 pre-validate posture). It strips a leading frontmatter block from the prose half, because templates carry frontmatter for `--list` but the emitted `<threadId>.md` must be clean prose.
- **The consumer is `spec create --from-template <name>`.** It resolves the bundled template via the same `DocCache.get` the `template` verb uses, splits it, and funnels `{ proseBody, factoryBody }` through the **identical** validate (`validateSpecBody`) → `writeSpec` → auto-commit path as the `--from-file`/`--factory-from-file` shape — no second authorial channel. The three input flags are mutually constrained: `--from-template` XOR (`--from-file` AND `--factory-from-file`). This is the agent-facing extension of §6.1's "route authoring through the canonical template verb" rule.
- **Bundled templates MUST parse clean under the CURRENT factory rules — pinned by golden tests.** Every markdown asset under `docs/templates/` (both the combined workflow templates and the `bead-factory-spec.md` scaffold) is shipped content whose factory body is subject to the same `parseSpecFactory` rules as any authored spec — including the §10.7 gate-output MUST. Conformance is NOT automatic from "the verb ships with the validator": the template asset is a separate file that can drift when a factory rule tightens. A golden test per template pins it (`tests/bead-factory-template.test.ts` for the scaffold, `tests/workflow-template-asset.test.ts` for `leasing-inbound-comms`), asserting the asset both parses and yields the intended bead set. **Binding: when a factory rule changes (a new parse-time MUST, a schema field), the bundled templates are part of the blast radius — update and re-green their golden tests in the SAME change.** Discovery (2026-07-06): the 0.11.0 §10.7 promotion shipped without touching `bead-factory-spec.md`, whose scaffold `step_final` was an `actor: human` bead with no `outputs:` — the shipped scaffold parsed clean before 0.11.0 and threw `SpecFactoryError` after, caught only later by the golden test. The scaffold's own field-reference comments now teach the §10.7 requirement so authors who rename the placeholders don't reintroduce it.

### 5.3 On-disk topology

Bead files do **not** live in the user's working-branch checkout. Praxis maintains a hidden git worktree on the `praxis-sync` branch; bead files reside there:

```
/zeroclaw-data/workspace/                          ← praxisRoot AND gitRoot (§5.1)
├── .git/
│   └── hooks/post-commit                          ← installed by `praxis project install-hooks`
│                                                    (PRAXIS_PROJECT_BOOTSTRAP_COMMAND in
│                                                     apps/clawcraft/domain/praxis-commands.ts)
├── .praxis/
│   ├── config.yml                                 (committed on the user's branch)
│   ├── workspaces/                                (committed on the user's branch)
│   └── data-sync-worktree/                        ← GITIGNORED on the user's branch
│       ├── .git → ../../.git/worktrees/data-sync-worktree
│       ├── .praxis/data-sync/issues/<id>.md       ← bead files live HERE
│       │                                            (on the `praxis-sync` branch)
│       ├── .praxis/data-sync/specs/<threadId>.md          ← prose body (§5.2.2)
│       ├── .praxis/data-sync/specs/<threadId>.factory.md  ← factory body (v1.13.6, §5.2.2)
│       ├── .praxis/data-sync/executions/<id>.json ← execution rows (§10 — v1.10.0)
│       └── .praxis/data-sync/validations/<id>.json← validation rows (§9 — v1.11.0)
└── .projection-queue/                             ← failure queue for the projection chain (§6.4)
    ├── <sha>.json                                   payloads that failed to POST — drained
    │                                                 oldest-first on the next successful push
    └── .log                                         per-attempt structured stderr
```

Source-of-truth references: `packages/praxis/src/lib/paths.ts:5–24` (topology comment), `paths.ts:319` (`resolveDataSyncDir` — the indirection from `praxisRoot` to the worktree), `resolveExecutionsDir` (executions/), `resolveValidationsDir` (validations/ — v1.11.0).

Implications:

- `writeBead(dataSyncDir, bead)` (e.g. `cli/commands/create.ts:192`) writes into the worktree. The user's working-branch checkout never sees the bead file in its tree.
- A commit on the user's working branch would have nothing praxis-related to commit.
- The commit that closes the projection loop is made **inside the worktree**, on the `praxis-sync` branch. Git worktrees share `.git/hooks/` with the main repo by default (§6.3 shared-hooks invariant), so the worktree commit fires `<gitRoot>/.git/hooks/post-commit` → `praxis project push` → projection → Convex. This is the entire mechanism (§6.2).
- Anyone reasoning about producer-side praxis behavior MUST start from this topology. Conflating "the user's branch" with "where bead files live" is the recurring failure mode when diagnosing producer-side bugs — §6.3 distinguishes the two "sync" mechanisms most often confused.
- `.projection-queue/` is a sibling of `.praxis/`, NOT a child — and deliberately so. It sits under the workspace root because that is the PVC mount the non-root pod user owns; the parent `/zeroclaw-data/` is root-owned and unwritable. The queue holds projection payloads that failed to POST — producer-side failure-resilience state, not bead data. §5.1's "Convex MUST NOT touch `.praxis/`" rule extends in spirit: Convex MUST NOT touch `.projection-queue/` either. Mechanics in §6.4.
- **Execution rows are JSON, not Markdown.** Beads and specs are Markdown-with-frontmatter (authored prose + structured metadata). Execution rows are JSON records — typed state (`status: "in_flight" | "completed"`, `specVersionGitSha`, `triggerPayload`, `terminalReferenceBeadId`) with no prose body. The projection emitter carries them as an additive `executions?: ExecutionChange[]` field on the payload (§10.5). See §10.2 for the file layout and `packages/praxis/src/cli/lib/paths.ts:resolveExecutionsDir` for the path-resolution helper.
- **Validation rows are JSON, not Markdown** (v1.11.0). The `praxis.validation/v1` shape (`schemaVersion`, `id`, optional `requestId` Convex-correlation key, `specPath`, `specContentHash` (sha256 hex), `startedAt`/`completedAt` (epoch ms), `status: "ok" | "blocking" | "warnings_only" | "partial" | "error"`, `stagesRun`, `semanticSkipReason?`, `modelVersion?`, `findings[]`, `priorWorkBeads[]`) lives at `<dataSync>/validations/<id>.json`. Written ONLY by `praxis spec verify --persist` (daemon-internal, §6.1). The projection emitter carries them as an additive `validations?: ValidationChange[]` field on the payload; Spec 4b's Convex `spec_validations` writer is the consumer. Status literals MUST match the Convex `spec_validations.status` enum verbatim (producer/consumer polysemy guard, per methodology §1).

- **MUST** produce exactly one commit on the `praxis-sync` worktree branch at the end of every write command. (NB: the prior `spec activate-execution` precedent is no longer parallel — that verb is now agent-facing per the rule above; `--persist` and friends remain daemon-internal on their own merits, not by analogy.) Snapshot test in `apps/clawcraft/test/unit/domain/claw-workspace.test.ts` enforces absence in both `PRAXIS_AGENT_COMMANDS` shapes AND the rendered TOOLS.md.

- **MUST NOT** advertise the auto-commit opt-out (`--no-sync`) on the agent-facing surface. The flag exists at the CLI level (`packages/praxis/src/cli/cli.ts:75`) as a power-user / test escape hatch but **MUST NOT** appear in `PRAXIS_AGENT_COMMANDS`. The agent learns "praxis writes propagate automatically" with no flag in its mental model. Generalizes: if a tool can be self-completing, opt-outs are for power users and stay off the agent surface — this is the minimal-surface principle, also relevant to memory and web search (see `claw-doctrine.md` §5.7).

- **MUST** pre-validate write-command inputs using the same parsers the projection / downstream consumer uses, before any disk write. Precedents: `writeBead` runs `BeadSchema.parse(bead)` (`src/file/storage.ts:188`); `decompose` and `verify` run `parseSpecFactory(markdown)` (catching `SpecFactoryError` → `CLIError`); `spec create`/`spec update` run `parseSpecFactory` + `parseSpecTriggers` via `src/cli/lib/spec-validate.ts:validateSpecBody`; `writeValidationRow` runs `ValidationRowSchema.parse(row)` (v1.11.0). The rule: if a downstream consumer (projection, factory materializer, anything else) parses the same payload, the write command MUST run the same parse first and exit non-zero on failure. A silent write whose payload is later rejected out-of-band (projection log, queue replay, etc.) starves the producer of the feedback it needs to self-correct — the agent's tool call returns success and it iterates blind. Surfaced 2026-05-16 by `praxis-specs-first-class` post-merge smoke (three iterations of malformed `## Bead Factory` / `## Triggers` bodies that the agent never knew failed); compliance vehicle: `fix(praxis): pre-validate spec body` (`88c844d`).

The pre-validate rule above closes the *iterates-blind* gap (the agent learns its body failed); this rule closes the *iterates-at-all* gap (the agent gets the shape right first try) — but the authoritative source is the `praxis template` verb, which ships *with* the validator and documents every field (`id`, `title`, `type`, `depends_on`, `actor`, `outputs`, branches, …), not a curated subset. ("Ships with the validator" makes the verb the single source of the field *documentation* — it does NOT by itself keep the scaffold *asset* conformant when a parse rule tightens; that guarantee comes from the §5.2.4 golden-test pin, not from co-location. See the 2026-07-06 §10.7 drift there.) A hardcoded example duplicated into TOOLS.md is strictly worse on three axes: it drifts from the validator, it omits fields, and it contradicts the AGENTS.md surface that already points at the verb (two surfaces, two answers — the drift this rule forbids). Discovery context: a prior attempt (`ae14b56`) hardcoded a `SPEC_FACTORY_EXAMPLE` const into TOOLS.md before the `praxis template` verb was noticed on the AGENTS.md surface; superseded by this commit. ### 6.1a Loose prose hygiene (warning-only)

§6.1's pre-validate rule covers *structural correctness* (factory YAML, triggers YAML, data-flow refs) — those throw `CLIError` exit 2 and block the write. This subsection covers the parallel **prose-hygiene** rule: the natural-language body has a canonical reading shape, and the CLI surfaces drift from that shape as a non-blocking warning the agent converts to a user-question on its next turn.

The contract is intentionally loose. Specs at `praxis spec create` time often pre-date the user's full understanding of edge cases / triggering conditions / desired outcomes — the hygiene loop is the mechanism by which the agent walks the user from a half-specified spec to a complete one across several turns. Blocking the write would force premature completeness; warning-only lets the spec land and iterate.

**Canonical four-header set** — the prose body MUST converge on these H2 anchors. The pure scanner at `packages/praxis/src/core/validation/spec-prose-hygiene.ts:scanProseHygiene` enforces exact-match (`^##\s+<header>\s*$`), case-sensitive:

| Header | Carries | Question the CLI prompts when missing |
|---|---|---|
| `## Summary` | 1–2 sentence elevator pitch | "How would you describe this spec in one sentence?" |
| `## Walkthrough` | Numbered narrative of what happens when it fires | "Walk me through what happens when this fires — step by step." |
| `## Edge cases` | Enumerated "what about X" cases the user wants handled | "What should happen on edge cases (empty input, partial failure, repeat trigger, etc.)?" |
| `## Triggers` | Natural-language description of when it should (and shouldn't) fire | "When should this fire? Any conditions that should NOT fire it?" |

`## Triggers` deliberately appears in both files — prose for narrative, factory for the YAML declaration. The agent uses one to verify the other; that is the cross-referencing capability this rule enables.

**Sole writers.** `praxis spec create` and `praxis spec update` are the only verbs that invoke the scanner. Both call it AFTER `autoCommitWorktree` succeeds, so the worktree commit boundary is unaffected and the projection chain (§6.2) fires regardless of hygiene state. The write succeeded; the warning is purely informational.

**CLI emit shape.** When `scanProseHygiene(body).missing` is non-empty, the CLI writes a single block to stdout:

```
Hygiene warnings (non-blocking — ask the user):
  • <Header> missing — <suggested question>
  • ...
```

Plain text (no ANSI), one bullet per missing header, terminating newline. Empty scan → empty string → nothing written. Exit code is unchanged; the command still returns 0.

**Agent-loop expectation.** TOOLS.md's "Spec hygiene loop" H3 (rendered by `apps/clawcraft/domain/claw-workspace.ts:renderPraxisSection`) teaches the agent the three-step loop:

1. Read the `Hygiene warnings` block from the CLI's stdout.
2. On the next turn, surface the suggested question(s) to the user.
3. Fold the user's answer into a follow-up `praxis spec update`. Repeat until the warning block stops appearing.

Each warning is a **prompt for the user**, not a gap the agent should silently fill in — the four headers exist precisely to capture user-supplied content the agent cannot author unilaterally (edge cases the user cares about, the user's mental model of when it should fire).

**Rules:**

- **MUST** invoke `scanProseHygiene` on `proseBody` after a successful write in every command that writes a spec prose body. The current set is `spec create` and `spec update`. A future verb that writes prose without going through these two MUST add the call; the projection / read paths MUST NOT.
- **MUST NOT** translate a hygiene warning into an exit-code or a blocking error. The whole point is to let the write land and iterate; promoting a warning to an error reintroduces the premature-completeness failure this rule is designed to avoid.
- **MUST NOT** auto-fill missing prose sections from the agent's own context. Doing so silently severs the user-as-source-of-truth invariant the rule encodes; the four headers map to four classes of user-supplied content (summary intent, walkthrough narrative, edge-case enumeration, trigger description), and synthesizing them from the agent's interpretation of the conversation defeats the cross-referencing capability.
- **MUST** keep the scanner pure (`src/core/validation/`) per §3.2. Any I/O — color, file reads, env lookups — belongs in the CLI emit wrapper (`src/cli/lib/spec-hygiene-emit.ts`), not in the scanner. Backstop: `tests/node-free-core.test.ts`.
- **MUST** render the four-header set + the loop expectation in TOOLS.md's "Spec hygiene loop" H3. Without TOOLS.md surface, the warning lands in the agent's tool transcript with no binding instruction on how to act on it. Snapshot test in `apps/clawcraft/test/unit/domain/claw-workspace.test.ts` enforces presence of the H3 + all four header literals + the warning-block prefix.

**Compliance vehicle.** Initial landing: `quick-spec` iteration, 2026-05-19. The §6.1a rule is enforced by:

- Pure-scanner contract: `packages/praxis/tests/validation/spec-prose-hygiene.test.ts` (exact-match + case-sensitivity + multi-word header + trailing-punctuation rejection).
- Render-surface contract: the "Spec hygiene loop" assertion in `claw-workspace.test.ts`.
- Wire contract: the CLI-side `formatProseHygieneWarnings` invocation after `autoCommitWorktree` in `spec-create.ts` and `spec-update.ts`.

### 6.3 Terminology — two distinct "sync" mechanisms

The word "sync" is overloaded in praxis. Distinguish them; the two share only a branch name (`praxis-sync`):

| Mechanism | Purpose | Trigger | Load-bearing for clawcraft UI? |
|---|---|---|---|
| `praxis sync` (the CLI subcommand) | Git-remote synchronization of the `praxis-sync` branch — fetch, merge, push to the configured remote. Cross-machine durability for bead data. | Manual or scripted; not invoked by write commands. | **No.** The clawcraft pod typically has no remote configured for `praxis-sync`; running this in-pod attempts a remote push that fails-gracefully (auto-saves to outbox). |
| **The projection chain** (post-commit hook → `praxis project push` → Convex) | Producer-side propagation of bead state into the clawcraft control plane so the UI updates reactively. | Automatic on every worktree commit (auto-fired at the boundary of every write command per §6.1). | **Yes.** This is the load-bearing path. |

Conflating the two is the recurring failure mode when diagnosing "praxis didn't update the UI." The right question is "did the worktree commit fire the post-commit hook?" — not "did `praxis sync` run?"

**Shared-hooks invariant.** Git worktrees share the `hooks/` directory with the main repo by default. A commit inside `.praxis/data-sync-worktree/` fires `<gitRoot>/.git/hooks/post-commit` — that is the entire mechanism by which a worktree commit reaches the projection. Reconfiguring `core.hooksPath` per-worktree (or any other change that decouples worktree hooks from main-repo hooks) silently breaks the projection chain. MUST NOT do so.

### 6.4 Projection transport — endpoint resolution and env-stripping resilience

Two non-obvious facts govern how the post-commit hook actually reaches Convex. Both were established empirically by the `praxis-link-local-dev-wiring` follow-up (`docs/tasks/completed/praxis-link-local-dev-wiring/`, commits `211fd0e` + `00b752c`); both have **silent-failure modes** — the hook runs, exits 0, and nothing surfaces the break.

**1. The projection targets the Convex HTTP-action site, not the API site.** Convex splits its surface across two hostnames:

| Surface | Host / port | Serves |
|---|---|---|
| API site | `.convex.cloud` / `:3210` | queries + mutations from clients (`CLAW_CONVEX_URL`) |
| HTTP-action site | `.convex.site` / `:3211` | HTTP actions — the `/api/praxis/projection` route lives HERE |

POSTing the projection to the API site returns **HTTP 405**. The producer resolves the site URL in priority order: `--url` flag → `$CLAW_CONVEX_SITE_URL` → `$CLAW_CONVEX_URL` rewritten (`:3210→:3211`, `.convex.cloud→.convex.site`). Source: `packages/praxis/src/cli/commands/project.ts:resolveEndpoint`.

**2. The hook resolves URL + token from `config.toml`, not from the environment.** The zeroclaw daemon strips `CLAW_*` environment variables when spawning agent-side tool subprocesses. An agent-fired post-commit hook therefore sees `CLAW_CONVEX_URL` unset and `CLAW_CONVEX_TOKEN` / `CLAW_PRAXIS_TOKEN` empty — with nothing in env, the push reports `{kind:'misconfigured'}` and silently no-ops. The installed hook (`packages/praxis/src/projection/hook-template.sh`) sidesteps env propagation entirely by reading both values directly from `/zeroclaw-data/.zeroclaw/config.toml` — the same file the daemon itself reads. Token priority: `$CLAW_PRAXIS_TOKEN` → `pre_shared_token` from `config.toml`. URL priority: `$CLAW_CONVEX_SITE_URL` → `send_url` from `config.toml` (path-stripped + site-rewritten).

- **MUST NOT** "simplify" the hook to rely on `CLAW_*` environment variables. The daemon's env-stripping makes that a silent-failure path — the hook runs, the push no-ops, no projection, no surface signal. The `config.toml` read is the binding resilient path.

**3. Failure queue.** When the push fails (Convex unreachable, auth rejected, 5xx, or `misconfigured`), the payload is written to `/zeroclaw-data/workspace/.projection-queue/<sha>.json` and the hook still exits 0 — it never fails the commit. The queue drains oldest-first on the next successful push. The queue lives under the **workspace root**, not at `/zeroclaw-data/.projection-queue/`: the parent `/zeroclaw-data/` is root-owned and not writable by the non-root pod user; `/zeroclaw-data/workspace/` is the PVC mount the pod owns. Topology in §5.3.

### 6.5 Agent Surface Contract — manifest, modes, envelope, next_action

§6.1 codifies the *behavior* rules for individual agent-facing verbs (auto-sync, pre-validate, minimal-surface, etc.). This section codifies the *contract* the entire agent surface presents as a single data structure — the four primitives that let the agent discover what it can call and how to follow continuations without orchestration prose in its prompt.

The contract was implicitly introduced by rnk-9mjj (manifest registry as first-class data) and rnk-tt8f (envelope + `next_action`); this section formalizes the rules so any future verb addition / mode change / continuation-emitter follows the same shape.

**The four primitives.** Each is binding; the source of truth lives in `packages/praxis/src/cli/manifest/types.ts`.

| Primitive | Type | Where it lives | Tests pin it |
|---|---|---|---|
| `agent_safe` | `boolean` (per-verb opt-in) | `meta.agent_safe` in each `src/cli/commands/<verb>.ts` | `tests/manifest/registry-completeness.test.ts` (every command has `meta`) |
| `modes` | `ReadonlyArray<'author' \| 'execute'>` | `meta.modes` in each command file | `tests/manifest/list.test.ts` (per-mode partitions) |
| `JsonEnvelope` | `{data, next_action}` wrap on `--json` | `cli/output/envelope.ts:writeJsonEnvelope` + `cli/lib/output.ts:OutputManager.data` | `tests/cli/json-envelope.test.ts` + `tests/manifest/cli-smoke.test.ts` |
| `NextAction` | discriminated union: `call` / `agent_work_then_call` / `null` | `manifest/types.ts:NextAction` | `tests/cli/next-action.test.ts` (4 execution-path emitters) |

#### `agent_safe` — per-verb opt-in policy

- **MUST** default to `false`. A new verb is host-only / daemon-internal until its `meta.agent_safe` is explicitly flipped to `true`. This forces a per-verb policy decision rather than letting "newly added" silently become "agent-callable."
- **MUST NOT** be the only gate on a verb's introspected flags. Daemon-internal flags (`--persist`, `--request-id`, `--connected-tools`; see §6.1) on otherwise agent-safe verbs are scrubbed by the manifest's flag introspection so the agent sees the verb but not those flags. Promoting `agent_safe: true` does NOT promote every flag on the verb.
- **MUST** be auditable: `praxis manifest list --json` returns only `agent_safe: true` verbs by default; `registryEntries()` (internal) exposes the full set including `agent_safe: false` for tests and host-side rendering.

#### Mode taxonomy — `author` and `execute`

- `author` (spec authoring loop): `manifest`, `spec create`, `spec list`, `spec show`, `spec update`, `spec verify`, `update`.
- `execute` (DAG-walk + bead lifecycle): `blocked`, `close`, `create`, `decompose`, `execute`, `list`, `manifest`, `project`, `ready`, `reopen`, `search`, `show`, `spec activate-execution`, `spec show`, `update`, `verify`.
- Modes are **intent partitions, not capability partitions**: `--mode=execute` returns everything an agent in execute-intent might call, not a tighter security boundary.
- A verb MAY belong to multiple modes — `manifest`, `update`, and `spec show` are in both today. The `Mode` JSDoc in `manifest/types.ts` mirrors this list; updates to either MUST land in the same PR (rnk-pce1 precedent).
- The verb's `meta.modes` array is the source of truth; the `--mode <m>` filter just intersects.
- `agent_safe: false` verbs are excluded from `listManifest()` regardless of mode — `meta.modes: []` is acceptable on host-only verbs and means "not exposed in any mode."

#### `JsonEnvelope` — wrap policy on `--json`

```ts
interface JsonEnvelope<T = unknown> {
  readonly data: T;            // verb's payload (verb-specific shape)
  readonly next_action: NextAction | null;
}
```

- **MUST** wrap every `agent_safe: true` verb's `--json` output in `{data, next_action}`. Bare invocations (no `--json`, no `PRAXIS_AGENT_INVOCATION=1`) are byte-identical to the pre-envelope shape — the envelope is opt-in.
- **MUST** route the wrap through one of two canonical sites — no verb implements its own envelope:
  - `OutputManager.data(data, textFormatter, nextAction?)` for verbs with BOTH a human text mode AND a JSON mode. The wrap is automatic when `ctx.json` is true; the formatter runs otherwise. Most read-shaped verbs use this path.
  - `writeJsonEnvelope(ctx, data, nextAction)` for raw-JSON-only verbs (the four execution-path emitters in §10.5). Bare-mode emits the unwrapped `data` as a compact JSON line.
- **MUST** preserve bare-mode output byte-identical to the pre-envelope shape. Subprocess-level smoke tests pin this (e.g. `tests/cli/json-envelope.test.ts > bare invocation ...`, `tests/manifest/cli-smoke.test.ts > bare manifest list ...`).
- `PRAXIS_AGENT_INVOCATION=1` env var defaults `--json` to true. The pod sets it so the agent gets envelopes without remembering the flag; humans don't set it, so terminal use is unchanged.

#### `NextAction` — the continuation contract

```ts
type NextAction =
  | { kind: 'call'; tool: string; args: Record<string, unknown> }
  | { kind: 'agent_work_then_call';
      factory_id: string;
      agent_hint: string;
      output_contract: Record<string, unknown>;
      then: { tool: string; args_template: Record<string, unknown> }; };
// null = terminal — no further action.
```

- `kind: "call"` — the agent invokes `<tool>` with `<args>` as-is. Direct continuation; used when the next step is fully determined by the current verb's state.
- `kind: "agent_work_then_call"` — the agent does work matching `agent_hint` (a free-form natural-language hint) against `output_contract` (the JSON shape the work must produce), then invokes `then.tool` with `then.args_template` filled in from the work output. Used when the next step requires LLM reasoning between calls.
- `null` — **no action THIS turn** (post-0.11.0: NOT necessarily "done"). The agent's turn ends legally on `next_action: null`; zeroclaw treats null as an unconditional turn-end and **never inspects `data`** (verified — memory `project_zeroclaw_continuation_semantics`). Three distinct null shapes, disambiguated by the `data` payload the agent reads:
  - **bare null** (`data` carries no `parked`/`unresolved` block) — genuinely done. Read verbs, `manifest`, and `verify --execution` run-close return this.
  - **`data.parked`** — a PARK: the walk is suspended at a human/timer/event boundary and is RESUMABLE across turns (minutes to weeks; §10.5). `data.parked` names the park `kind`, `dueAt`, `parkedAt`, and per-bead `resolve_hint`s telling the agent why and how to resume.
  - **`data.unresolved`** — close-BLOCKED: `verify --execution` (JSON mode) found beads that can neither complete nor be legally archived (the §10.9 D12 envelope). Carries the blocking beads + a hint naming `praxis verify --execution <id> --abandon`.
- **Target-match rule (Option A — zero zeroclaw change).** The PARK shape (`next_action: null` + `data.parked`) is emitted by **`execute` ONLY** — never by `update`, `verify`, or any other verb. `update` keeps emitting its execute continuation unconditionally; the NEXT `execute` call is what parks. The Option-A rationale: because null is an unconditional turn-end and `data` is never inspected by zeroclaw, the park needs zero runtime change — null ends the turn, and `data.parked` tells the AGENT (not zeroclaw) why and how to resume (§10.5 resume triggers). A non-null park, or a park emitted from a non-execute verb, is forbidden (§8).
- **MUST** stay a closed discriminated union. New continuation kinds require a doctrine amendment in the same PR — the agent's loop parses `kind` exhaustively, so adding a kind without updating the loop is a silent failure.
- **SHOULD** render per-kind handling instructions into the agent-facing surface (`claw-workspace.ts:renderAgentsTemplate`, "Standing orchestration rule"), not just a terse "perform `next_action`." A generic instruction is enough for `kind: "call"` (mechanical) but underspecifies `agent_work_then_call`, where the agent must (a) do the `agent_hint` work **in the same turn** using its own tools, then (b) invoke `then.tool` — *not* announce the work in chat and yield the turn. The surface SHOULD name that anti-pattern explicitly. **This guidance is a best-effort guardrail, NOT a sufficient control.** Empirical finding (2026-06-04): the per-kind instruction does **not** prevent the stall on a weak model. Dev trace `f3246a74` first surfaced it — on `agent_work_then_call` the agent emitted "Step 1: … fetching now." as a terminal assistant message and ended the turn, abandoning the execution mid-walk (summarize bead never completed; execution id in no later trace). After the per-kind guidance was rendered live, trace `e54257b3` **reproduced the identical stall** ("Bead `v4v4` (summarize) is ready. Fetching your last 5 emails." → turn ends, execution abandoned). **The model that stalls is the ROOT orchestrator — `xiaomi/mimo-v2.5-pro` (`claw-config.ts:REASONING_MODEL`) — not a delegated sub-agent.** The stall occurs at the root *before any delegation*: in both stall traces every llm.call is mimo and `delegate` is never called, so the `mail` sub-agent (`AGENTIC_TOOL_MODEL = google/gemini-3.1-flash-lite-preview`) never runs. It is the root reasoning model that reads past the prose. The runtime relies on the model reading `next_action` and acting; it does not auto-drive `agent_work_then_call`. **The binding fix is therefore runtime-side: the agent loop MUST auto-drive `agent_work_then_call` (force the work + `then.tool` call, or refuse to end the turn while a non-null `next_action` is pending) rather than trusting the model to follow prose.** Tracked as cross-repo follow-up `rnk-h6g3` (zeroclaw). The rendered AGENTS.md guidance stays as a guardrail a capable model honors, but it is not load-bearing — `rnk-h6g3` is.
- §10.5 lists the four execution-path emitters and the verifier-failure-still-continues invariant — that section is authoritative for *which* `next_action` each execution verb returns (including the decision-variant `args_template` with no `state` key, §10.8); this section is authoritative for the *shape* contract. The `NextAction` union itself is unchanged by the decision contract — the variants are `args_template`/`agent_hint` content, within-contract per this section.

#### Manifest registry as single source of truth

- `praxis manifest list/show` is the canonical agent-surface discovery verb. Registry-derived (no hand-maintained allowlist), unit-tested per-mode, end-to-end smoke-tested via subprocess.
- **MUST** co-locate `meta: VerbMeta` with every command in `src/cli/commands/`. The registry walks the commander program tree, joins each `Command` to its `meta`, introspects positionals/flags, and emits a `VerbDescriptor` row. `tests/manifest/registry-completeness.test.ts` enforces presence.
- **MUST** keep introspection programmatic. The registry does NOT carry hand-typed flag descriptions for any agent-safe verb — flag descriptions are the literal commander `.option(...)` `description` arg, so they cannot drift from the runtime behavior.
- `PRAXIS_AGENT_COMMANDS` (`apps/clawcraft/domain/praxis-commands.ts`) **is no longer the agent's verb catalog — that role is retired** (`rnk-rwfn`, finishing the `rnk-p7a0` retirement). The standalone TOOLS.md "Command surface" list it used to render is gone; the manifest snapshot in AGENTS.md is the single agent-facing verb catalog. The constant persists only as the single-source for the handful of verb *literals* TOOLS.md usage-prose names inline (§6.1) — `spec activate-execution` is correctly absent from it (it never was, and need not be: the manifest is the catalog). The 2026-05-19→06-09 trace history that motivated the move: the duplicate list drifted from the manifest (e.g. `spec activate-execution` manifest-only) and re-sent two divergent verb surfaces on every agent turn.

## 7. Operational Runbook — Bumping Praxis in Production

The full chain to ship a new praxis version to running pods:

### 7.1 In `clawcraft` (this repo)

1. Bump `packages/praxis/package.json#version` to the new semver.
2. Commit on `main`: `praxis: bump to <new-version>`.
3. Tag: `git tag praxis-v<new-version>`.
4. Push: `git push origin main --tags`.
5. The publish workflow fires on the tag push. Watch via `gh run watch`.
6. Confirm the new version on the registry: `gh api /orgs/soulbound-labs/packages/npm/praxis/versions`.

### 7.2 In `zeroclaw` (the sibling fork)

7. Bump `PRAXIS_VERSION` ARG in `Dockerfile` (Wolfi `release` stage) to match.
8. Commit on `main`: `image: bump praxis to <new-version>`.
9. CI builds a new image, tagged with the git SHA, pushed to GCP Artifact Registry.

### 7.3 In `clawcraft` again (Convex env)

10. `pnpx convex env set CLAW_DOCKER_IMAGE <new-image-uri-with-sha>` against the prod deployment (`colorful-rook-584`).
11. Existing pods either await natural restart or are rolled by triggering `restartPodForIntegration` / `scaleUp` per pod.

### 7.4 Sequencing — TOOLS.md / binary parity

If a praxis bump *also* changes the rendered TOOLS.md section (e.g., new commands added to `PRAXIS_AGENT_COMMANDS`), the clawcraft Convex deploy MUST happen *after* the new ZeroClaw image is rolling. Otherwise the agent reads "use new command X" but the binary doesn't have it yet.

The reverse is also a hazard: updating `praxis-commands.ts` (TOOLS.md changes) without bumping the praxis version causes the agent to read commands the installed binary doesn't recognize.

The safe ordering is always: **ship the binary first, ship the agent's awareness of the binary second.**

**Wire-shape direction rule (D7, 0.11.0).** When a praxis bump *also* changes the projection wire shape that Convex consumes, the deploy order depends on the *kind* of change — it is NOT always "binary first":

- **UNION-widening (a producer adds a new literal the consumer's guard/schema must already tolerate) → Convex FIRST.** Example: praxis 0.11.0's new `status: "abandoned"` literal and the parked-snapshot block. A pod emitting `abandoned`/parked against an OLD (un-widened) Convex guard would `400`-reject the user's ENTIRE projection (not just the new field). So the tolerant consumer — Convex with the widened guard/schema — deploys first, THEN praxis publish → ZeroClaw `PRAXIS_VERSION` bump + pod roll → AGENTS.md awareness.
- **REQUIRED-field add (a producer starts emitting a field an old consumer doesn't know to send) → Convex LAST.** This is the §7.4 binary-first case above (the v1.13.6 `factoryMarkdown` precedent): the binary must emit the new required field before Convex's hard-break guard demands it.

The mnemonic: **a new-producer-literal vs old-consumer-guard change is the MIRROR IMAGE of a required-field add** — widen the consumer first, narrow the consumer last.

### 7.5 Rollback

To roll back a praxis version in production:

1. Identify the previous green image SHA (the one `CLAW_DOCKER_IMAGE` pointed at before the bad bump).
2. `pnpx convex env set CLAW_DOCKER_IMAGE <previous-sha>`.
3. Roll pods.

The bad praxis version remains on the registry permanently (immutability §4.1) but is no longer reachable via any deployed image. Cut a new patch tag with the fix; do not attempt to re-publish the bad version.

### 7.6 Known bootstrap asymmetry — prod assumes pre-existing `.git/`

The dev and prod paths that install the post-commit hook are **not symmetric** around `git init`:

| Path | Behavior |
|---|---|
| Local dev (`infra/scripts/dev/render-claw-config.ts:327–378`, `installPraxisLinkHook`) | Runs `git init -q -b main` against `workspaceDir` if `.git/` is missing, then invokes `praxis project install-hooks --workspace <workspaceDir>`. |
| Prod (`PRAXIS_PROJECT_BOOTSTRAP_COMMAND` in `apps/clawcraft/domain/praxis-commands.ts:27–39`, fired via `lifecycle.postStart` in `convex/clients/gke.ts:buildDeploymentSpec`) | Now mirrors the dev path (closed below). Pre-fix behavior: checked the tripwire and ran `install-hooks` only, assuming `.git/` already existed at `/zeroclaw-data/workspace/`. |

Failure mode: a fresh prod pod booting against a PVC that doesn't already have `.git/` will silently fail to install the hook (the install path errors out internally; the postStart `|| true` suppresses it). The agent then runs `praxis create`, the bead writes to the worktree, no hook fires, no projection, no UI update — and there is no obvious surface signal pointing at the missing `.git/`.

Mitigations available today:

- The auto-commit helper introduced by `docs/tasks/completed/praxis-issues-auto-sync/` skip-not-fails on missing `.git/` (so the praxis command itself still succeeds); but the producer→UI propagation does not happen.
- `praxis doctor` surfaces a missing `.git/` if invoked.

**Closed** (2026-05-15) by `docs/tasks/completed/praxis-prod-git-bootstrap/`: `PRAXIS_PROJECT_BOOTSTRAP_COMMAND` now mirrors the dev path — `git init -q -b main` when `.git/` is missing, then idempotent repo-scope identity config (`user.email`, `user.name`, `commit.gpgsign false`), then the existing `install-hooks` tripwire. Per `infra-doctrine.md §15.24`, the dev path remains the *behavioral* template; the prod command is its shell-side mirror, not a shared abstraction (necessarily different execution shapes — Node `execFileSync` host-side vs. a single `sh -c` embedded in K8s `lifecycle.postStart`). The failure-mode and mitigation paragraphs above are preserved as historical context.

**Follow-up closed** (2026-05-15): the bootstrap also runs `praxis setup --auto --prefix=claw --no-gh-cli` if `.praxis/config.yml` is missing. Without this step, every `praxis <verb>` (`list`, `create`, etc.) fails the `requireInit` gate with "Not a praxis repository" because the gate looks for `.praxis/config.yml`. Pre-fix, the workspace was a git repo but not a praxis repo — surfaced when the thread-spec-binding rollout drew operator attention to the praxis CLI in the running container. Both `PRAXIS_PROJECT_BOOTSTRAP_COMMAND` and `installPraxisLinkHook` were updated symmetrically. The `claw` prefix yields bead IDs like `claw-r3k8x2`; `--no-gh-cli` skips the GitHub CLI hook install (not needed in the pod environment).

**Second follow-up closed** (2026-05-22): the 2026-05-15 closure was *incomplete*. The PVC mount root `/zeroclaw-data/workspace` is created by the kubelet as `root:nogroup` (uid 0, gid 65534 via the pod's `securityContext.fsGroup`). The `claw` container runs as `nobody` (uid 65534). Git's dubious-ownership security check (introduced in Git 2.35) refuses every command on a worktree whose root isn't owned by the running user — including the bootstrap's `git config user.email/name` (exit 128, `fatal: not in a git directory`) AND every subsequent agent-fired `praxis update`'s `simple-git` auto-commit. The failures were invisible because (a) the bootstrap's `|| true` swallowed every error, (b) repo-scope `safe.directory` doesn't help — git won't load repo config until it passes the ownership check, and (c) `--global` `safe.directory` writes fail too because `HOME=/zeroclaw-data` is unwritable by `nobody`. Surface: bead files written to `.praxis/data-sync-worktree/...` were staged but never committed; the post-commit hook never fired; the projection chain stayed silent; the task panel never updated for the full lifetime of every affected pod. The dev path escaped this because Docker Desktop's bind-mount UID remapping makes the container see workspace files as owned by uid 65534 — the dubious-ownership check passes natively in dev; this is the third dev/prod divergence behind §15.24's parity rule (alongside the in-container praxis watcher and the wget healthcheck). Closed by chowning the workspace root to `65534:65534` in the `config-init` init container — init containers default to root and now mount the workspace PVC. `chown` is non-recursive on purpose: only the worktree root triggers Git's check; everything inside is either created by the main container as 65534 or covered by `fsGroup`. Companion change in `apps/clawcraft/domain/praxis-commands.ts:PRAXIS_PROJECT_BOOTSTRAP_COMMAND`: every step now uses `… || echo "praxis-bootstrap: <step> FAILED …" >&2` instead of `|| true`, so any future regression is visible in `kubectl logs <pod> -c claw` rather than silent. `exit 1` was rejected as the failure shape — `lifecycle.postStart` non-zero exits crashloop the container under the K8s default policy, trading silent breakage for noisy outage. See `infra-doctrine.md §6.6` for the init-container topology change.

Catalog-awareness lives in the host; praxis stays catalog-agnostic. |

## 9. Validation Pipeline

The validation pipeline is praxis's second authorial channel for `beads`. It runs structural + capability checks against a spec and emits findings + `role: "prior_work"` bead recommendations. Semantic checks are out of praxis's scope — the host (clawcraft) is responsible for them and injects findings into the persisted row via the CLI's `--inject-semantic` flag (§9.7). This section documents the foundation (pipeline shape, the single adapter port, types, spec-state derivation, two-writer rule, fingerprint-stable reconciliation); invocation sites and the trigger model land in v1.9.1 (Spec 2b).

### 9.1 Scope

The mechanical pipeline has two orthogonal dimensions, composed in parallel by a single function:

1. **Structure** — parses the spec body's `## Bead Factory` block; reports DAG cycles, dangling deps, malformed YAML as blocking findings.
2. **Tools** — asks an injected `CapabilityRegistry` whether each tool referenced by the factory beads is installed for the user; missing tools become blocking findings *and* yield `role: "prior_work"` beads via fingerprint-stable upsert.

A third dimension — **semantic** — exists on the persisted `ValidationRow` but is host-emitted, not pipeline-emitted. Semantic findings land on the row via the CLI's `--inject-semantic <path>` flag (§9.7): the host reasons about the spec body, writes a JSON envelope of `semantic_mismatch` findings, and `praxis spec verify --inject-semantic <path>` merges them into the persisted row. Praxis-core itself runs no LLM — that's a deliberate boundary (praxis 0.7.0). The pipeline is pure: all I/O lives behind the single `CapabilityRegistry` port.

**Grounded semantic (praxis 0.8.0).** The host runs the pipeline **twice** per Validate click: first as a mechanical pre-pass (`praxis spec verify --thread <id> --json`, read-only) whose stdout JSON the agent captures, then as the persist pass (`praxis spec verify --persist --inject-semantic <path>`) after the agent has reasoned. The semantic reasoning in between is *informed by* the pre-pass's structure + tools findings — the agent does not re-emit findings the mechanical pipeline already caught; it surfaces only the semantic gaps mechanical can't see (prose-vs-factory intent drift, missing beads the outcome implies, factory steps the prose does not motivate). The composer enforces `--connected-tools` parity between the two invocations so the pre-pass and the persist pass see the same tool-capability oracle. See §9.10 step 5.

### 9.2 Location and structure

| Surface | Path | Binding |
|---|---|---|
| Pipeline function | `packages/praxis/src/core/validation/pipeline.ts` | pure; node-free; ESLint boundary rule enforces; `tests/node-free-core.test.ts` walks `core/validation/*` as a runtime backstop |
| Adapter ports | `packages/praxis/src/core/validation/ports.ts` | `CapabilityRegistry` interface only; clawcraft provides the Convex-backed implementation. The `SemanticEvaluator` port was retired in praxis 0.7.0 — semantic is host-emitted via `--inject-semantic`. |
| Types | `packages/praxis/src/core/validation/types.ts` | `Spec`, `Finding` (discriminated union, includes the host-injectable `semantic_mismatch` variant), `ValidationResult`, `PriorWorkBead`, `FindingSchema` (Zod, gates `--inject-semantic` reads) |
| Spec body validator | `packages/praxis/src/core/validation/spec-body-validator.ts` | extracted from `cli/lib/spec-validate.ts` per the Spec 3 portion; pure; CLI wraps with `CLIError` exit-code mapping |

### 9.3 Output contract

`validateSpec(spec, factory, deps) → { findings, priorWorkBeads }` — mechanical findings only. Host-injected semantic findings are merged in by the CLI at the persist boundary (§9.7), not by the pipeline.

- Each `Finding` carries `{ source: "structure" | "tools" | "semantic", kind, blocking, message, ... }`. Structure + tools findings are `blocking: true`; the `semantic_mismatch` variant (host-injected only) is `blocking: false`.
- Each `PriorWorkBead` carries `{ validationFingerprint, title, description, beadType: "next-action" }` ready for `internal.specValidation.upsertPriorWorkBead` to materialize.
- `canActivate` is UI-derived from the persisted-row findings — it is not a field on `ValidationResult` itself.

**Status mapping rule** (binding on the CLI's `deriveValidationStatus` and on the Convex consumer): status is computed from the union of mechanical + injected findings on the persisted `ValidationRow`.

| Findings on the row | `status` |
|---|---|
| any `blocking: true` finding | `"blocking"` |
| at least one non-blocking finding (e.g. injected `semantic_mismatch`), zero blocking | `"warnings_only"` |
| zero findings | `"ok"` |

`"partial"` is reachable only if a host injects a stage-degraded sentinel (no such finding kind ships today; the literal is retained on the `spec_validations.status` enum for forward compatibility with a future "degraded host" signal). `"error"` is reserved for the CLI's catastrophic-fail path.

### 9.4 Spec state machine

Spec state is binary: `active | inactive`. The derivation lives at `packages/praxis/src/core/spec-state.ts:deriveSpecState({ openPriorWorkBeads, liveBlockingFindings })`. A spec is `active` iff both inputs are empty. The materialized snapshot lives on `specs.active?: boolean` so agent-runtime queries don't walk findings + beads on every read; Spec 2b's post-projection and post-validation triggers maintain it.

### 9.5 Two-writer enforcement

The validation pipeline writes to `beads` exclusively via `internal.specValidation.upsertPriorWorkBead`. That mutation hardcodes `writer: "validation"` + `role: "prior_work"` and refuses to overwrite a bead at the same fingerprint whose existing `writer !== "validation"`. The companion projection writer (`internal.praxisLink.applyProjection` → `upsertBead`) asserts `insertShape.writer === "workspace"` + `insertShape.role === undefined`. The combined assertions are the runtime invariant; §5.2's per-table writer enumeration is the doctrine surface.

**Validation-mirror workspace beads (5d + 5e).** Steps 5d (create) and 5e (close) of the validate lifecycle (§9.10) have the agent author and reconcile `next-action` beads with `metadata.assignee = "user"` and title prefix `Validation [<threadId>]:` to surface human-actionable findings the user must resolve (enable an integration, fix the spec, install a tool). These beads ride the workspace authorial channel (`writer: "workspace"`, no `role`) — distinct from the pipeline's validation-source prior_work beads (`writer: "validation"`, `role: "prior_work"`) — so they do NOT collide with the two-writer rule. Duplication risk is contained two ways: (1) the agent's 5d prompt explicitly excludes any finding whose key matches a 5a `priorWorkBead` entry, so the validation channel and the workspace channel cover disjoint finding sets; (2) the agent's deterministic title format + `praxis search` dedupe pre-check makes repeated Validate clicks idempotent (≤1 workspace bead per finding-message across N clicks). **Convergence (5e).** Step 5e closes prior validation-mirror beads whose trailing message fragment is no longer present in this run's union of `5a.findings[].message` ∪ `5b.envelope.findings[].message`, gated by the triple guard (non-terminal state + `assignee = "user"` + title prefix). The 5d→5e pair makes the workspace channel **converge** with the live finding set instead of monotonically growing — a user who resolves the underlying problem (connects gmail, edits the spec) sees the bead auto-close on the next Validate click. The triple guard prevents collateral damage: pipeline-authored `prior_work` beads have no `assignee = "user"` and so are never touched by 5e (they are reconciled exclusively by `reconcileValidations` on the projection side, §9.7). The `--assignee user` convention is the same literal the execution-runtime verifier uses (`packages/praxis/src/cli/commands/update.ts:456`); §6.1's MUST roster gains a new entry by surface — `praxis create` (writer-with-assignee) and `praxis close` are already on the agent surface (both `agent_safe: true` in the manifest, §6.5; `create` also single-sourced as a TOOLS.md prose literal in `PRAXIS_AGENT_COMMANDS`), no new flag was needed.

### 9.6 Fingerprint-stable reconciliation

The pipeline owns the `validationFingerprint` algorithm (`computeFingerprint` in `pipeline.ts`). Both `upsertPriorWorkBead` (writer) and `closeStalePriorWorkBeads` (reconciler) receive the fingerprint from the pipeline output — neither recomputes it. The reconciler's contract: for a user, archive every validation-source bead whose `validationFingerprint` is absent from `keepFingerprints`. This produces idempotent upsert + lossless cleanup across re-runs of the same spec.

### 9.7 Invocation sites and adapter wirings

Spec 4b collapsed the Convex-side pipeline invocation. Today the pure mechanical pipeline (§9.2) has **one authoritative caller** — `praxis spec verify` pod-side — and Convex never imports praxis core runtime values.

| Caller | File | Registry | Stages on the persisted row |
|---|---|---|---|
| `praxis spec verify --thread <id> [--json] [--persist] [--connected-tools <list>] [--inject-semantic <path>]` (pod-side; the daemon-internal flags MAY appear on `--persist` invocations the agent composes from the validate intent map — see `claw-doctrine.md` §5.6.1 v2.34.0 + §9.10 below) | `packages/praxis/src/cli/commands/spec-verify.ts` | `NoopRegistry` (no `--connected-tools`); CLI-side `ListCapabilityRegistry` (with `--connected-tools`, comma-list passed from the agent) | structure + tools always; `semantic` iff `--inject-semantic` was supplied |

The single caller runs in **two modes**, both invoked by the composer in the same agent turn (praxis 0.8.0 — see §9.10 step 5):
- **Read-only mode (step 5a — `--json` without `--persist`):** the CLI runs the mechanical pipeline and writes `{ findings, priorWorkBeads }` JSON to stdout for the agent to capture and ground its semantic reasoning on. No row is written. Exit 10 on blocking findings is expected (agent proceeds).
- **Persist mode (step 5c — `--persist [--inject-semantic <path>]`):** the CLI re-runs the mechanical pipeline (idempotent — composer enforces `--connected-tools` parity between modes), merges injected semantic findings, and writes the `praxis.validation/v1` row.

With `--persist`, the CLI writes a `praxis.validation/v1` `ValidationRow` to `<dataSync>/validations/<id>.json` and fires the worktree-commit boundary; the projection emitter carries the row in an additive `validations?: ValidationChange[]` field on the payload, and Convex's `internal.praxisLink.reconcileValidations` (Spec 4b) is the consumer.

**`--inject-semantic <path>` contract (praxis 0.7.0).** The flag MUST be used together with `--persist`; standalone use errors. The path is a JSON file with the envelope `{ modelVersion?: string, findings: Finding[] }`. Each finding is validated against the canonical `FindingSchema` (Zod) at the read boundary — malformed JSON or unknown finding kinds reject the whole inject and no row is written. Validated findings append to the mechanical findings before `writeValidationRow`; `stagesRun.semantic` flips to `true`; `modelVersion`, if supplied, is persisted on the row for downstream host-side caching.

**Retired callers (Spec 4b + praxis 0.7.0).** The pre-4b Convex action `internal.specValidationActions.runValidation` is gone. The `ConvexCapabilityRegistry`, `ZeroClawSemanticEvaluator`, and `CachedEvaluator` adapter classes are gone. `apps/clawcraft/convex/specValidationActions.ts` is gone (entire file deleted). `apps/clawcraft/convex/clients/zeroClawDaemon.ts` (the `postValidate` + `postExecuteStart` clients) is gone. The `SemanticEvaluator` port + `runSemanticStage` + `semantic_skipped` Finding variant + `SEMANTIC_SKIP_REASONS` literal type + `ValidationRow.semanticSkipReason` field + CLI's `--semantic` / `--from-file` daemon shape were all deleted in praxis 0.7.0 — semantic is now host-emitted via `--inject-semantic`. The Convex side keeps a V8-isolate `internal.specValidation.runValidation` *mutation* (NOT an action; no praxis runtime import); its semantic-cache hot path is now host-owned (no longer correlated with a retired praxis port — see backend-doctrine §3.5). Cache hits and the `validation_semantic_cache` table remain on disk pending a separate cleanup.

The UI mutation `api.specValidation.requestValidation` (Validate button in `apps/clawcraft/src/components/tasks/ValidationTab.tsx`) is still a thin scheduling wrapper — it now schedules `internal.specValidation.runValidation` (the V8 mutation), not the retired action. ### 9.10 Validation runtime via `/webhook` dispatch + `[CLAWCRAFT_TRIGGER]` envelope convention

Post-Spec-4b + praxis-0.7.0 + envelope-collapse (claw-doctrine §5.6.1 v2.34.0) lifecycle for a single Validate click on a cache miss. **The five-step grounded-semantic agent turn (5a–5e below) is the canonical orchestration for the full validate verb but is no longer inlined per click by the Convex composer.** The agent discovers it via `praxis manifest show "spec verify"` + this section + the intent-map routing in AGENTS.md (`Intent: validate` → `praxis spec verify --thread <ThreadId>`). The composer's job is now to *signal* the click; the *what* of the walk is the agent's own knowledge.

1. User clicks Validate. `api.specValidation.requestValidation` schedules `internal.specValidation.runValidation` (V8 mutation).
2. `runValidation` checks `validation_semantic_cache(userId, specContentHash, CURRENT_MODEL_VERSION)` (host-owned; no longer correlated with a praxis port). On miss, schedules `internal.webhookDispatch.sendValidationWebhook` (V8 action).
3. `sendValidationWebhook` reads `users.{containerStatus, preSharedToken}` and the spec's `threadId`, composes a `[CLAWCRAFT_TRIGGER]` envelope (`Source: validate-button` + `Intent: validate` + `ThreadId: <id>` — < 300 bytes, see claw-doctrine §5.6.1 v2.34.0 for the full shape), and POSTs `{ sender, content }` to the in-cluster nginx gateway (`<WS_GATEWAY_URL>/relay/{userId}` → pod:42618/webhook). The composer no longer reads the user's integrations, the spec body, or the factory body; the `--connected-tools`/`--persist`/`--request-id`/`--inject-semantic`/TOOL CATALOG CONTEXT machinery is now the agent's concern, discovered through `praxis manifest show "spec verify"` and the validate verb's own continuation envelope. The "TOOL CATALOG CONTEXT as host-side soft enrichment" idea (catalog × user-enablement matrix the composer used to embed so the semantic stage could surface `/integrations?connect=<provider>` deep-links) is host-side state the agent now fetches on demand if it needs to ground its reasoning; the validation-resolver protocol (claw-doctrine §5.6.2) still handles the user-facing `[INTEGRATION_LINK]` button render.
4. The pod's `/webhook` handler injects the message into the agent loop. The agent recognizes the `[CLAWCRAFT_TRIGGER]` envelope, looks up `Intent: validate` in AGENTS.md's intent map, and walks the five-step flow below (5a–5e) — same handler used when the user types "validate" in chat.
5. **Five-step grounded-semantic agent turn (praxis 0.8.0):**
   - **5a.** The agent runs the mechanical pre-pass `praxis spec verify --thread <threadId> --connected-tools <list> --json` via its shell tool. The CLI runs the mechanical pipeline (structure + tools) and emits `{ findings, priorWorkBeads }` as JSON to stdout. Exit 0 on no findings; exit 10 with parseable JSON when blocking findings exist (both are expected — the agent proceeds to 5b in either case). If stdout is not parseable JSON, the agent surfaces the failure in its one-line summary and SKIPS 5b–5c.
   - **5b.** The agent reasons about the embedded spec body for semantic mismatches between its natural-language intent (## Outcome, ## Why) and the mechanical ## Bead Factory, **informed by 5a's mechanical findings AND the TOOL CATALOG CONTEXT block** (the catalog × user-enablement matrix the composer embedded — see step 3). It does NOT re-emit findings the mechanical pipeline already caught (cycles, dangling deps, missing tools by explicit `tool_id:`) — those are already destined for the persisted row via 5c. It surfaces only semantic gaps mechanical can't see: (i) prose-vs-factory intent drift, missing beads the outcome implies, factory steps the prose does not motivate, AND (ii) **unconnected-tool reliance** — when the spec's prose or factory implies a tool category the user has not connected (per the TOOL CATALOG CONTEXT), the agent emits a `semantic_mismatch` with a `/integrations?connect=<provider>` deep-link. This is the "next-action" the user sees in the validation panel; it is intentionally a finding, not a bead — keeping the next-action surface composer-side (no new praxis CLI finding kinds, no `priorWorkBead` materialization from semantic). Writes a JSON envelope `{ modelVersion: "<model id>", findings: [{ source: "semantic", blocking: false, kind: "semantic_mismatch", message: "...", confidence: 0..1 }, ...] }` to `/tmp/praxis-inject-<requestId>.json`. If no semantic mismatch, the `findings` array is empty.
   - **5c.** The agent runs `praxis spec verify --thread <threadId> --persist --request-id <uuid> --connected-tools <list> --inject-semantic /tmp/praxis-inject-<requestId>.json` via its shell tool. The CLI re-runs the mechanical pipeline (idempotent — same `--connected-tools` as 5a guarantees the same mechanical findings), validates the injected findings against `FindingSchema`, merges them into the row, flips `stagesRun.semantic = true`, writes a `praxis.validation/v1` row to `<dataSync>/validations/<id>.json`, and fires the worktree-commit boundary (§6.1 — auto-sync). If the inject file is missing or malformed, the CLI exits non-zero and no row is persisted; the agent's one-line summary surfaces the failure to the operator.
   - **5d.** The agent materializes **human-actionable validation-mirror beads** from the findings just persisted. For each finding F observed in 5a's JSON or written in 5b's envelope, the agent INCLUDES F if (a) `F.blocking === true` (any kind, mechanical or semantic), OR (b) `F.kind === "semantic_mismatch" && F.confidence >= 0.7`. It EXCLUDES any F whose key matches an entry in 5a's `priorWorkBeads` array (the pipeline already authored a validation-source bead for it; the workspace bead would duplicate the user-facing task — see §9.5 footnote). For each included F, the agent composes the EXACT title `Validation [<threadId>]: <F.message>` (deterministic — same finding text yields the same title across Validate clicks), runs `praxis search "<exact title>"` to dedupe, and only if no open bead matches the exact title runs `praxis create "<title>" -t next-action --assignee user -d "Spec: <threadId>. <F.message>"`. The deterministic title is the idempotency primitive: repeated Validate clicks on unresolved findings produce ≤1 bead per finding even though the agent runs `praxis create` every turn. The choice of `--assignee user` matches the established convention from the execution-runtime verifier (`packages/praxis/src/cli/commands/update.ts:456`), where the literal `"user"` is the "tagged for human" marker.
   - **5e.** The agent reconciles **prior validation-mirror workspace beads** against this run's finding set so the workspace channel *converges with* live findings rather than monotonically growing. It runs `praxis search "Validation [<threadId>]:"` (prefix search) to enumerate every workspace bead 5d has ever authored for this thread across past Validate clicks. For each returned bead B that satisfies all three guards — (i) B.state is non-terminal (NOT one of `done | closed | archived`), (ii) `B.metadata.assignee === "user"`, (iii) `B.title` strictly starts with the literal `Validation [<threadId>]: ` — the agent extracts `M = B.title.substring('Validation [<threadId>]: '.length)`. It builds `NEW_MESSAGES` = the union of `findings[].message` from 5a's JSON output AND 5b's envelope. If `M ∉ NEW_MESSAGES`, the agent runs `praxis close <B._id>` — the finding has been resolved (user connected the integration, edited the spec, installed the tool). If `M ∈ NEW_MESSAGES`, the bead is left alone (5d's title-dedupe will skip the no-op re-create). The triple guard prevents collateral damage: pipeline-authored `prior_work` beads carry no `assignee = "user"` and are therefore never closed by 5e (they are reconciled exclusively by `reconcileValidations` on the projection side, §9.7 — two-writer rule preserved). The final reply summary appends `; <N> bead(s) created, <M> bead(s) closed` so the operator can audit both directions.
6. The next git push triggers the praxis-link projection emitter, which carries the row as a `ProjectionValidationChange` in the `validations` array of the projection payload. **Producer-side finding reshape** (v1.11.1): `packages/praxis/src/cli/projection/payload.ts:reshapeFinding` lifts each praxis-core flat `Finding` (`{source, kind, blocking, message, ...}`) into the nested `ValidationChangeFinding` shape (`{severity, blocking, finding: {kind, ...}}`) the Convex consumer's schema demands. Severity derives from `(blocking, kind)`: blocking → `"blocking"`; `semantic_skipped` → `"info"`; else → `"warning"`. Without this transform the consumer's `isValidationFinding` guard rejects the whole projection as `bad-payload` and the validation never lands.
7. `internal.praxisLink.applyProjection` → `reconcileValidations` (Spec 4b §3.6) lands `spec_validations` + `validation_findings` rows, reconciles `prior_work` beads (two-writer rule preserved — bead writes still use `writer: "validation"`), and flips `specs.active` per `(canActivate && priorWorkBeads.length === 0)`. Idempotent on replay via `by_user_praxis_validation_id` (`praxisValidationId = requestId ?? id`).
8. The UI's `latestForSpec` subscription flips, the Validate button re-enables, and findings render.

**Latency: 10–30s wall-clock on cache miss (pod wake + agent latency + projection + Convex commit).** Cache hit: ~50ms (single Convex commit).

**`[system]` prefix convention.** A new single-byte signal on the `/webhook` `{message}` shape:

- Convex-issued directives MAY start the message body with the literal token `[system] ` (note the trailing space). The agent treats `[system]` -prefixed messages as authoritative instructions (rather than user-channel conversation) and is expected to execute the embedded literal shell command.
- There is **no typed payload schema** and **no dispatch catalogue**. The body is natural-language; the agent's existing intelligence parses it. Spec 4b intentionally rejected the v1.0.0 architect proposal to introduce typed `body.type` discriminators + a `domain/webhook-payloads.ts` catalogue — the existing `{message: string}` shape is sufficient.
- v1 trust posture: any caller that can POST to `/webhook` with a valid bearer can issue `[system]` directives. Validation + execution kicks already require the bearer; a malicious user with chat access could plausibly type `[system] Please run: <cmd>` themselves and the agent might honor it. The blast radius is bounded (the user's own pod runs the command; most `praxis` commands are already in the agent's tool surface). Hardening options for v2: HMAC signature on Convex-issued directives, pod-side rule that only `/webhook` POSTs from known sender IPs carry `[system]` weight, or parse-time rejection of user chat messages starting with `[system]`. Out of v1 scope.
- The claw-doctrine §5.x convention note (Spec 4b) documents the receiver-side semantics; backend-doctrine §6.5 documents the Convex-side composition.

The retired pre-4b dedicated `POST /api/validate/spec` + `POST /api/execute/start` Rust handlers are gone (or never landed on the pod — Spec 3b shipped graceful 404 against `/api/execute/start` and that brief was never built). The `/webhook` channel is the sole Convex→pod direction post-4b.

## 10. Execution Runtime

The execution runtime is the third (and final v1) consumer of praxis's `## Bead Factory` block. The validation pipeline (§9) decides *whether a spec is activatable*; the execution runtime decides *what happens when an active spec is run*. Both share the same factory parser and bead types; only the lifecycle and authorial channel differ.

### 10.1 Scope

- **Consumes**: §9-active specs (specs whose `specs.active === true`); reads factory + bead defs through the pinned `specVersionGitSha` recorded on the execution row.
- **Walks**: the factory DAG via per-bead executors (the agent runtime), one bead at a time, in dependency order.
- **Closes**: by materializing a single terminal `reference` bead whose `fields.contentUri = "praxis://execution/<id>"` and patching the execution row to `status: "completed"` (success) or `status: "abandoned"` (the honest unfinishable terminal — §10.9).
- **Parks**: at human/timer/event boundaries, suspending the walk across turns (the multi-turn parked-walk lifecycle — §10.5); a parked run stays `in_flight` with its `parked` snapshot set.
- **Does NOT**: trigger validation (orthogonal — validation is the activation gate); auto-retry failed beads; host its own timer (the pod-side agent-cron + the every-activation due-scan drive resume — §10.5; NO Convex cron).

### 10.3 On-disk shape (`praxis.execution/v1`)

Each execution row is a JSON file at `.praxis/data-sync-worktree/.praxis/data-sync/executions/<id>.json`. Written atomically (temp-file + rename). Schema:

```ts
interface ExecutionRow {
  readonly schemaVersion: 'praxis.execution/v1';
  readonly id: string;                    // ULID
  readonly specPath: string;              // `<threadId>.md`
  readonly specVersionGitSha: string;     // pin per §9-equivalent
  readonly startedAt: number;             // epoch ms
  readonly completedAt: number | null;    // completion ONLY (never abandon)
  readonly abandonedAt: number | null;    // 0.11.0 (D6) — additive optional
  readonly abandonReason: string | null;  // 0.11.0 (D6) — additive optional
  readonly status: 'in_flight' | 'completed' | 'abandoned';  // TERNARY
  readonly parked: ParkedSnapshot | null; // 0.11.0 (D1) — the park discriminator; null while running or after unpark
  readonly triggerPayload: unknown;       // opaque, spec-author-defined
  readonly triggeredBy: 'user_request';   // v1 only (reserved literals deferred)
  readonly terminalReferenceBeadId: string | null;
}

interface ParkedSnapshot {
  readonly kind: 'human' | 'timer' | 'event';   // PARK_KINDS (closed)
  readonly dueAt: number | null;                // epoch ms; null for human/event (no clock boundary)
  readonly parkedAt: number;                    // epoch ms the run last parked
  readonly beads: ReadonlyArray<{                // per-bead resume affordance
    readonly short_id: string;
    readonly factory_id: string;
    readonly resolve_hint: string;
  }>;
}
```

**Polysemy guard (methodology §1).** `status` is a closed TERNARY `in_flight | completed | abandoned` — each literal deliberately chosen to AVOID collision with `users.{podState,containerStatus}: "running"` and `beads.state: "done"`. **`parked` is NOT a status literal** (D1) — a parked run stays `in_flight`; the optional `parked: ParkedSnapshot | null` field is the discriminator (§10.4 anti-pattern note). `abandonedAt`/`abandonReason` are DISTINCT from `completedAt`, which stays completion-only. Producer-side (this on-disk shape), projection emitter (§10.2), AND consumer-side (Spec 3b's Convex `executions` table) MUST all carry the same three status literals plus the `parked`/`abandonedAt`/`abandonReason` fields. Drift between any two surfaces re-introduces the polysemy bug; the `abandoned` literal is a union-widening add, so Convex (the tolerant consumer) deploys FIRST (§7.4).

### 10.4 Execution state machine

TERNARY closure (0.11.0):

```
in_flight ──verify --execution──────────────> completed   (every bead resolved-for-close)
   │   ↑
   │   └── (park/unpark: status STAYS in_flight; `parked` field set/cleared — see below)
   │
   └── verify --execution --abandon ─────────> abandoned   (run cannot finish — §10.9)

   (per-bead FAILURES route through bead `waiting_for` — see §10.9; no `failed` row state)
```

- `in_flight` — written by `spec activate-execution`. Walker is in charge. Covers BOTH actively-walking and parked runs.
- `completed` — written by `verify --execution <id>` on the success path (every bead `isResolvedForClose`). Terminal reference bead exists; `completedAt`/`terminalReferenceBeadId` populated.
- `abandoned` (0.11.0, D6/D8) — written by `verify --execution <id> --abandon --reason <why>`: the honest terminal for a run that cannot finish. `abandonedAt`/`abandonReason` populated; `parked` cleared; unresolved beads archived `metadata.disposition: 'abandoned'`; a terminal reference bead carries `abandon_reason`. Idempotent on an already-abandoned row; refuses a `completed` row.

There is **no `failed` state on the execution row**. Per-bead failures route to `waiting_for` + `assignee: user` (§10.9).

**Parked is a derived predicate, NEVER a status literal (D1, anti-pattern note).** A parked run keeps `status: "in_flight"`; the discriminator is the optional `parked: ParkedSnapshot | null` field. There is no `status: "parked"` literal — adding one is forbidden (§8) and would re-introduce the polysemy the §10.3 guard exists to prevent. "Is this run parked?" is answered by `row.parked !== null`, not by a status comparison.

**Bead-level satisfaction + park classification (single-sourced).** Both "this bead no longer blocks the walk" AND "this bead parks the walk" are implemented exclusively in `packages/praxis/src/core/bead-satisfaction.ts` and consumed by the walker (`computeFrontier`), the `execute` continuation emitter, and the `verify --execution` close gate. A static single-source test forbids literal terminal-state comparisons in those files — post-0.11.0 it ALSO forbids inlined `=== 'waiting'`, so park/needs-user classification cannot drift out of the predicate module.

Satisfaction (the §10.8 contract) has **two distinct meanings**:

- **Satisfies dependents** (`isSatisfiedForDependents`): `done`, OR a *resolved* decision (`clarified` + recorded `extensions.output` — §10.8). `archived` NEVER satisfies dependents — a superseded or skipped decision must not unblock its children.
- **Satisfied for close** (`isResolvedForClose`): `done`, OR a resolved decision, OR `archived` (skip/abandon disposition / supersession / legacy archive). An **unresolved decision blocks close**.

Park/gate classification (0.11.0) — the predicates that drive the four-way frontier (§10.5):

- `isHumanGate(bead)`: a bead whose `actor: human`, OR a `type: decision` bead — the human-resolution boundary (park `kind: human`).
- `isTimerParked(bead, now)` / `isEventParked(bead)`: a factory bead carrying a `wait:` block with `wait.kind: timer` (due-ness computed against `now`) / `wait.kind: event` (an external label).
- `parkKindFor(bead, now)`: resolves a parking bead to exactly one `PARK_KINDS` value (`human | timer | event`).
- `isAwaitingUserFix(bead)`: a `waiting` state + `assignee: user` bead — the §10.9 failure route / runtime safety net (the `needs_user` frontier class, distinct from a healthy human gate).

One-sentence state definitions for `type: decision` (methodology §1 sentence test):

- `clarified`: the decision bead is live and awaiting or holding its decision record.
- **resolved** (a predicate, not a state value): a clarified decision bead whose `extensions.output` is a recorded JSON object.
- `done`: impossible for decisions (the state machine pins `states: ['clarified','archived']`); for every other bead type, the work completed.
- `archived`: the decision record was superseded by another decision bead, or skipped.
- `skipped`: an execution bead archived with `metadata.disposition: 'skipped'` because its path was not taken (`update --skip`) — "branch not taken."
- `abandoned` (0.11.0, D8): an execution bead archived with `metadata.disposition: 'abandoned'` because the whole run was abandoned (`verify --execution --abandon`) — "died with the run." DISTINCT from `'skipped'`: the `disposition` enum is now `skipped | abandoned`, and the two are never interchangeable (`'skipped'` = a deliberate not-taken path within a healthy run; `'abandoned'` = a bead that never got the chance, because the run gave up).

Resolution is keyed on the recorded output, **never** on `decided_at` — every materialization path pre-stamps `decided_at` at bead birth, so its presence is meaningless as a signal (resolution restamps it as a side effect, suppressed when `--decided-at` is passed explicitly).

### 10.5 Lifecycle

End-to-end sequence for a single execution. Steps 1–3 describe the **button-trigger path**; the **chat-trigger path** (rnk-eelu) collapses steps 1–3 into a single agent-direct invocation of `praxis spec activate-execution <threadId>` and joins the sequence at step 4. Both paths converge on the same CLI verb and the same `ExecutionRow`.

1. **Trigger**. User clicks Run in the UI (Spec 3b's `ValidationTab` or equivalent surface).
2. **Convex action**. The UI mutation `api.specExecution.requestStart` (Spec 3b) checks `specs.active === true` (gate — praxis CLI cannot enforce this; no integrations table access); refuses with a typed error otherwise.
3. **Daemon spawn**. The Convex action calls the praxis CLI inside the pod via `postExecuteStart` (Spec 3b): `praxis spec activate-execution <threadId> --trigger-payload <json>`. (Chat-trigger path: the agent makes the equivalent CLI call directly per its standing manifest rule — no Convex hop, but the same verb.)
4. **Activate**. The CLI:
   - Pre-validates the spec body (`spec-body-validator.ts`) — including the data-flow integrity static check (`checkDataFlowStatic`), the branch_mode expression parse check (`checkBranchModeExpressions`), and referential-integrity checks on `branches:`/`on_fail:`/`on_threshold:` targets. On failure, exits 2 with a structured error; nothing is written. Beads carrying branch-authoring metadata additionally emit a non-fatal advisory warning (§10.8 — the walk performs no branch routing).
   - Mints a ULID for the execution.
   - Resolves `specVersionGitSha` from the praxis-sync worktree HEAD.
   - Writes the `ExecutionRow` (status: `"in_flight"`).
   - Decomposes the factory: one bead per declared factory entry, each carrying `metadata.execution_id = <id>` + `metadata.factory_id = <fb.id>`.
   - One auto-commit at the command boundary (§6.1).
5. **Ready-set loop**. The agent runtime calls `praxis execute --execution <id>` to get the ready-set (factory IDs whose state is `clarified`, that are not themselves already-resolved decisions, whose every parent **satisfies its dependents** — `done`, or a *resolved* decision per §10.4/§10.8 — AND every `$parent.output.<key>` ref resolves). For each ready bead, by type:
   - **Work bead** (any non-decision type): agent does the work (tool call / LLM reasoning), then calls `praxis update <short_id> --state=done --output '<json>'`.
   - **Decision bead**: agent decides, then records the decision with `praxis update <short_id> --output '<json>'` — **no `--state`** (decision beads reject `--state`; the recorded output IS the resolution, and the bead stays `clarified`).
   - **Not-taken-path bead** (a dependent the decision's recorded route bypasses): agent closes it with `praxis update <short_id> --skip --skip-reason "<why>"` → `archived` + `metadata.disposition: 'skipped'`. Never force it to `done`.
   - The auto-verifier (§10.7) runs inline against the bead's `verify:` rules on both completion shapes (work `--state=done` and decision `--output`); on success `extensions.output` is stamped (and `decided_at` restamped on decisions); on failure the bead retypes to `waiting-for` + assignee=user + failure metadata (§10.9).
   - Mutex (§10.6) serializes the write against any other in-flight update on the same execution.
6. **Close**. Once the ready-set drains, the agent calls `praxis verify --execution <id>`. The CLI:
   - Asserts every bead with `metadata.execution_id === <id>` is **satisfied for close** (`isResolvedForClose`, §10.4): `done`, a resolved decision (still `clarified`), or `archived`. An unresolved decision blocks close and is named in the error.
   - Materializes a terminal `reference` bead (`fields.contentUri: "praxis://execution/<id>"`, `metadata.execution_id` set).
   - Patches the execution row to `status: "completed"`, `completedAt: Date.now()`, `terminalReferenceBeadId: <ref bead's internal id>`.
   - Reports `data.satisfied` counts in the close payload — `{done, resolved_decisions, skipped, archived_other}`; `archived_other` (archives that are neither skips nor decision supersessions) exists for operator audit of escape-hatch archives.
   - One auto-commit. Idempotent on already-completed executions.

**Composer responsibility (signal vs walk-loop teaching).** The Convex composer (`apps/clawcraft/convex/webhookDispatch.ts:composeExecutionDirective`) no longer teaches the algorithm — it emits a tiny `[CLAWCRAFT_TRIGGER]` envelope (claw-doctrine §5.6.1 v2.34.0) carrying `Source: run-button` + `Intent: run` + `ThreadId: <id>` + `TriggerPayload: <json>` and lets the agent route through AGENTS.md's intent map to `praxis spec activate-execution <ThreadId> --trigger-payload '<TriggerPayload>'`. The three-phase walk loop (Phase 1 = step 4 activate, Phase 2 = step 5 ready-set/update loop, Phase 3 = step 6 verify-close) is the *agent's* knowledge — it comes from this section + the continuation-passing envelope below (`next_action` chain) + `praxis manifest show "spec activate-execution"`. Factory_id → short_id resolution is done by the agent parsing `praxis list --json` (filtering `.data[]` by `instance_key === executionId && factory_id === fid` — the envelope wraps the array under `data`; see "Continuation-passing envelope" below) — no `jq` dependency, no praxis CLI change. The spec body is on disk at `<threadId>.md` + `<threadId>.factory.md` under praxis's owned `.praxis/data-sync/specs/`; the agent uses `praxis spec show --thread <id>` to read it when it needs the factory's `agent:`/`description:`/`output:` fields rather than expecting the composer to embed them per click. Per-bead verifier failures route to `waiting-for + assignee=user` (§10.9) and the agent SKIPs to the next factory_id rather than aborting the walk — `waiting_for` is the always-on safety net.

**Multi-turn parked-walk lifecycle (0.11.0 — replaces the prior "one agent turn" framing).** A walk no longer necessarily runs to completion in a single turn. When `execute` finds the ready-set empty but a human/timer/event boundary unsatisfied, it emits the PARK exit (§6.5: `next_action: null` + `data.parked`) and the turn ENDS. The walk then resumes across turns — minutes to weeks. Park-and-resume chunking (a `wait:`-bearing bead, or a human/decision gate) is the sanctioned answer to the **32-tool-call-per-activation auto-drive budget**: a wide DAG that would blow the budget in one turn is split by inserting a park boundary, so each activation walks a bounded chunk.

THREE resume triggers, all **wake-gated** (a parked run on a sleeping pod resumes on next wake — the SLA is EVENTUAL, not timely):

1. **User chat / any activation (DUE-SCAN — the CORRECTNESS mechanism, D14).** The AGENTS.md standing rule runs `praxis execute --list` on every activation/webhook and resumes any in-flight execution whose wait is now satisfied. This scan — not the cron — is what guarantees a parked run eventually resumes; `execute --list` computes timer due-ness internally (the agent has no shell `date`).
2. **Pod-cron timer (an OPTIMIZATION, D14).** At park time the agent composes a self-addressed `[CLAWCRAFT_TRIGGER] … Intent: resume-execution … ExecutionId: <ulid>` envelope armed via the pod-side agent-cron. A cron fire merely *accelerates* the resume; if the cron never fires (pod asleep), the next due-scan catches it. Cron is never the sole resume path.
3. **Bead-resolve webhook (doctrine-registered, code DEFERRED).** A future praxis-intent-relay webhook wakes a run on external bead resolution. No dormant `Intent` literal ships in code today (§8 dormant-scaffolding); the trigger is registered here so the resume model is complete.

**NO Convex cron** (user mandate — §8). The timer host is the pod-side scheduler only.

**Timer-anchor caveat (accepted v1 drift).** A parent bead re-run *after* `wait_due_at` was stamped re-anchors the timer; recompute-on-re-run is deferred. Accepted for v1.

**Phase 0 VERIFIED (zeroclaw agent-cron, live).** Agent-cron fires into the FULL agent loop (not a bare callback); one-shot via `cron once <delay> --agent` / `cron add-at <RFC3339> --agent`; jobs persist in SQLite at `/zeroclaw-data/workspace/cron/jobs.db` on the PVC-mounted workspace (survives pod restart AND recreate); the scheduler runs a startup catch-up that replays missed fires. This is the substrate trigger (2) is armed against.

**Continuation-passing envelope (rnk-tt8f).** Every `agent_safe: true` verb wraps its `--json` output in `{data, next_action}` (the shape contract — `JsonEnvelope` + `NextAction` discriminated union + manifest registry single-source rule — is formalized in §6.5; this paragraph names *which* `next_action` each execution verb emits). `next_action` is `null` for terminal verbs (`manifest list`, `verify --execution`) and populated by the four execution-path emitters: `spec activate-execution`/`update --output`(on execution beads — both the work-bead `--state=done` shape AND the decision-resolution `--output`-only shape)/`update --skip` → `{kind:"call", tool:"praxis execute", args:{execution}}` **unconditionally** (update never parks — it always hands back to execute; the NEXT `execute` call is what parks if the frontier has drained to a wait boundary, per the §6.5 single-emitter rule); `execute --json` has **FOUR emitter exits** (0.11.0), in priority order: (1) `ready` non-empty → `{kind:"agent_work_then_call", factory_id, agent_hint, output_contract, then:{tool:"praxis update", args_template}}` — the `args_template` is **type-aware**: work beads get `{id, state:"done", output}`, decision beads get `{id, output}` with NO `state` key (the emitter may only emit calls `update` accepts; `data.ready` entries carry `{factory_id, short_id, type}`); (2) all beads `isResolvedForClose` → `{kind:"call", tool:"praxis verify", args:{execution}}` (close); (3) `ready` empty ∧ (`parked` ∪ `needs_user`) non-empty → **PARK exit**: `next_action: null` + `data.parked` (`kind`, `dueAt`, `parkedAt`, `beads[]` with per-bead `resolve_hint`) and the conditional snapshot WRITE; (4) true wedge (`ready` empty, nothing parked/needs-user, but not all closeable) → `next_action: null` + `data.parked` with a kind-LESS blocker listing and a hint naming `praxis verify --execution <id> --abandon`. `verify --execution` (close) → `null`. `execute --list` → `null` (a scan, never a continuation). The pod env sets `PRAXIS_AGENT_INVOCATION=1` (default `--json` to true) so the agent gets envelopes without remembering the flag. Critically, `update --output` emits the execute-continuation even when the auto-verifier failed (bead routed to `waiting_for + assignee=user`) — the loop continues; the next `execute` call returns an empty ready-set + the close continuation, and the failure does NOT abort the walk (§10.9 safety net still holds). The composer's walk-loop prose remains the canonical teach for production today; this envelope is the surface a future composer simplification (sibling task: AGENTS.md standing rule) will lean on to retire most of the directive. Bare invocations (no `--json`, env unset) are unchanged — the envelope is opt-in.

### 10.6 Per-execution mutex discipline

All `praxis update` writes within a single execution serialize through `withExecutionLock(executionId, fn)` (a `Map<execution_id, Promise>` in the daemon). Cross-execution updates parallelize.

- **No on-disk lock table.** No TTL sweep. No cross-restart durability.
- **Daemon restart semantics.** The map clears on process restart. An in-flight `update` call fails (the daemon process is gone); the bead remains in whatever transitional state the failure interrupted. Re-invocation by the agent surfaces the failure naturally (the bead is still `clarified` / `active`, not `done`); manual operator resolution via `praxis update --state=waiting_for --assignee user` reroutes to the §10.9 pathway.
- **Structured log** (advisory). The mutex emits `{"event": "exec_lock", "phase": "acquire" | "release", "execution_id", "bead_id", "ts"}` JSON lines to stderr on every acquire + release. Daemon log scrapers can join these to reconstruct intra-execution timelines.

The deliberate choice of in-process mutex over a durable lock table reflects v1's blast radius: a stuck execution costs the user a manual re-run, not data corruption — `waiting_for` is the always-on safety net.

### 10.7 Verifier contract

The verifier (`core/verifier.ts`) has two pure responsibilities:

1. **Inline YAML constraints** (`verifyOutput(rules, output)`) — evaluated on every execution bead at `praxis update --state=done` time (work beads) and at decision-resolution time (`praxis update --output` on a decision bead, no `--state` — §10.8). Supported rule shapes:
   - `must_have_keys: [string]` — output must contain all listed keys.
   - `<key>.type: "array" | "number" | "string" | "boolean" | "object"` — runtime type check.
   - `<key>.{gt|lt|gte|lte|eq|neq}: <number>` — numeric comparison.
   - `<key>.{min_length|max_length}: <number>` — array/string length.
   - `<key>.pattern: <regex string>` — regex match (string values).
   - Unknown rule keys surface as violations (FMEA #6 — silent pass would be a sandbox-class bug).
2. **Data-flow integrity** —
   - **Static** (`checkDataFlowStatic`, called from `spec-body-validator.ts` at decompose): every `$parent.output.<key>` reference declared in `inputs:` resolves to a key the named parent declares in `outputs:`.
   - **Runtime** (`checkDataFlowRuntime`, called from `execution-walker.ts` at ready-promotion): every declared reference's parent has actually produced the keyed output via a prior `praxis update --output <json>`.

The expression DSL (`core/execution-expr.ts`) is retained **solely for parse-time validation** — `checkBranchModeExpressions` (bead-factory.ts) checks `branch_mode: expression` syntax and the §8 sandbox rejections at spec parse. There is no runtime expression dispatch in v1 (the former branch-mode dispatch helper was retired 2026-06 with zero call sites; see §10.8).

**Structural-only in v1.** No LLM. No fuzzy matching. If the YAML constraints don't catch a regression, the failure surfaces downstream (in the human's review of the run's output) — semantic verification is a v2 brief.

**Gate-output MUST (0.11.0 — promoted from SHOULD).** Every `actor: human` bead OR `type: decision` bead MUST declare ≥1 `outputs:` key OR a non-empty `verify.must_have_keys`. Enforcement lives in the **pure core parser** — `checkGateOutputDeclarations` inside `core/bead-factory.ts:parseSpecFactory` (throws `SpecFactoryError`, exit 2, nothing written). Because it is in `parseSpecFactory` and not in any one command, it fires on **every** parse path that touches a factory body: `decompose`, `spec create --factory-from-file`, `spec create --from-template`, `spec activate-execution` pre-validation, AND every golden test that calls `parseSpecFactory`/`splitWorkflowTemplate` directly. (Do not describe this rule as "activate-execution pre-validation" only — that names one downstream caller of the shared validator, not where it is enforced.) This promotes the old route-bearing-decision SHOULD to a hard gate across ALL human/decision beads, and it **kills the vacuous `--output '{}'` self-approval**: a gate with no declared output key could be "resolved" by recording an empty object, which approved nothing. With a required key, a gate cannot be closed without an actual recorded decision the verifier checks. (Companion rule: `wait:` is REJECTED on `type: decision` and `actor: human|system` beads — §10.8 D5 — so a gate parks on the actor/decision discriminator, never on a `wait:` block.)

**actor ↔ resolved_by mapping (the §10.8 provenance gate).**

| Bead `actor` | Resolution requires | Accepted `--resolved-by` |
|---|---|---|
| `human` | `--resolved-by user` | `user` ONLY (a human gate must be approved by the human owner) |
| `system` | `--resolved-by <user\|system>` | `user` OR `system` (an agent-assertable system action — the asymmetry) |
| (none) | no `--resolved-by` | n/a — ordinary work bead |

The flag is required on completion (`--state done`), decision resolution (`--output`), AND `--skip` of any `actor: human\|system` bead (§10.8).

### 10.8 Decision bead resolution contract (flat model)

A decision bead placed inline in an execution DAG resolves by **recording its decision output** — nothing else:

1. **Materialization is flat.** `spec activate-execution` materializes a decision bead as one node per factory entry, exactly like every other type. `branches:` blocks are NEVER expanded into lazy children.
2. **Resolution** = `praxis update <short_id> --output '<json>'` (no `--state`). The recorded `extensions.output` is the single resolved signal (§10.4); the bead stays `clarified`. Any `--state` on a decision bead is rejected with a teaching error. The auto-verifier (§10.7) runs on the recorded output; `decided_at` is restamped as a side effect.
3. **Dependents** declare flat `depends_on: [<decision-id>]` edges — the sanctioned authoring shape (formerly called the "single-branch pin workaround"; it is now the contract). A *resolved* decision satisfies them (`isSatisfiedForDependents`); an `archived` decision never does.
4. **Not-taken paths** are closed with `praxis update <short_id> --skip [--skip-reason "<why>"]` → `archived` + `metadata.disposition: 'skipped'` + `metadata.skip_reason`. `--skip` is valid only on execution beads, mutually exclusive with `--state`/`--supersede`/`--ratified`/`--output`, and emits the execute continuation so the walk proceeds. Never force a not-taken bead to `done`.
5. **Supersession** stays the only archive path for the decision *record* itself: `--supersede=<other-decision-id>`. **Self-supersede is forbidden** (`ValidationError`) — it was semantically null and only ever "worked" as a deadlock-escape hatch.

**Actor-gate contract (`--resolved-by`, 0.11.0 — §10.7 mapping enforced here).** A bead with `actor: human|system` is a GATE. THREE resolution shapes all require `--resolved-by <user|system>`:

1. **Completion** — `praxis update <id> --state done … --resolved-by <user|system>`.
2. **Decision resolution** — `praxis update <id> --output '<json>' --resolved-by <user|system>`.
3. **Skip** — `praxis update <id> --skip … --resolved-by <user|system>`.

A `human` gate requires EXACTLY `--resolved-by user`; a `system` gate accepts `user` OR `system` (the asymmetry: a system gate represents an agent-assertable system action, so the agent may self-assert `system`; a human gate represents human intent and demands the `user` channel). Omitting `--resolved-by` on a gate raises a teaching `ValidationError` naming the bead + the rule + the corrected command + the literal directive "end the turn and ask — do not self-approve." On success, `metadata.resolved_by` is stamped.

**Provenance + forgeability honesty (FMEA-3).** `--resolved-by` is **AGENT-ASSERTED** — praxis cannot verify the assertion (it has no channel identity). The binding rule is therefore behavioral, not enforced: `--resolved-by user` may ONLY follow an approval received on an **authenticated owner channel** (web WS / native Telegram), NEVER content relayed from an envelope-external source (email/SMS bodies — those are untrusted payloads, not owner intent). Stated honestly: a residual forgeability risk remains (a misbehaving or prompt-injected agent *could* assert `user` without a real approval). v2 closes it — strict gates resolve only via an authenticated intent-relay webhook (no agent-asserted flag). v1 ships the flag as the lightest gate that makes self-approval an explicit, auditable act rather than a silent default.

**Wait-block parking (`wait:`, 0.11.0).** A factory bead may declare a `wait:` block to park the walk on a non-human boundary:

- `wait.kind: timer | event` (`human` parking derives from `actor: human`/`type: decision`, NOT from `wait:`).
- `wait.until` (timer) — an ISO-8601 DURATION (`P2D`, `PT2M`) anchored at the moment the wait arms, OR an RFC3339 datetime (absolute). Classified by `classifyTimerUntil` (hand-rolled in core — no node `Date`-parsing dep).
- `wait.event` (event) — an external label matching `[a-z0-9_.:-]+`.

`wait:` is **REJECTED at parse time on `type: decision` and `actor: human|system` beads** (D5) — those park on the actor/decision discriminator, and mixing a `wait:` block onto them would create two competing park signals. `update` stamps `metadata.wait_due_at` (epoch ms) on a timer-wait child when its LAST parent becomes satisfied (inside the execution lock, riding update's auto-commit) — anchoring an ISO-8601 duration at *now*, or resolving an absolute datetime. `activate-execution` does NOT stamp (it would mis-anchor a multi-day walk to activation time — §10.2).

**Advisory authoring metadata.** `branches:`, `branch_mode:`, `expression:`, `on_fail:`, and `on_threshold:` are advisory authoring metadata — parse-time validated (branch and escalation targets must name declared beads; `branch_mode: expression` syntax is checked) and surfaced as drift hints (`unselectedBranches` in `praxis verify`'s drift report), but the execution walk performs **no** branch routing: not-taken paths are closed with `praxis update <id> --skip --skip-reason`, and structural routing, if ever built, requires a new brief amending this section. The parser emits a non-fatal advisory warning (naming this section and the `--skip` remediation) on any bead carrying these fields.

**Retirement note (2026-06).** The former `branch_mode` walker semantics documented here (awaiting-agent/awaiting-user walker states, lazy branch-child materialization, and an update flag for recording the chosen branch that never existed in `update.ts`) and the branch-dispatch helper in `core/verifier.ts` were documented-but-dead: zero call sites, never wired into the walk. That drift produced the decision-bead deadlock exposed by the zeroclaw auto-drive fix (`rnk-h6g3`): the walker demanded `done`, the state machine forbade `done`, and the dead §10.8 bridge reconciled nothing, so every gated execution wedged at its first decision bead until the agent improvised (self-supersede, manual `--state active`). The dispatch helper and the runtime expression evaluator are deleted; the parse-time DSL validation remains (§10.7).

The expression DSL grammar is fixed (Spec 3a §3.4): literals, `$parent.output.<key>` refs, comparison/logical/arithmetic operators, ternary, parens. **No function-call syntax. No bare identifiers other than `true` / `false`.** §8 forbids any future DSL extension that relands eval/Function/vm/dynamic-import vectors.

`actor: human` decision beads keep the same data contract — nothing in this section precludes a human recording the resolution (via chat or pod terminal); interactive resolve affordances remain deferred to Spec 3c (§10.10).

### 10.9 Failure pathway

Every per-bead failure routes through bead `waiting-for` + `metadata.assignee: "user"`. No new state values are introduced. Failure-tracking metadata:

| Field | Set when | Purpose |
|---|---|---|
| `metadata.assignee = "user"` | Verifier rejects an output (work-bead `--state=done` or decision resolution `--output`). | Surfaces in the UI's "needs me" filter; signals the human owns the next step. |
| `metadata.failure_reason = "verifier_failed"` | `verifyOutput` rejects the bead's `--output <json>`. | Machine-parseable failure category. |
| `metadata.last_error = "<violation summary>"` | Same as above. | Human-readable joined-`;` summary of every violation. |

Decision-resolution verifier failures route through this same pathway (retype to `waiting-for` + assignee=user) — there is no decision-specific failure shape. `--skip` (§10.8) is a **disposition**, not a failure: it never sets `failure_reason` and never routes here.

Recovery: the user opens the bead in the UI, sees `failure_reason` + `last_error`, fixes the underlying issue (re-runs the work, edits the output, or amends the spec), and either re-runs `praxis update --state=done --output <corrected>` (work beads) / `praxis update --output <corrected>` (decision beads) or routes to a manual completion path. There is no auto-retry in v1.

**Abandon exit — the honest terminal (0.11.0, D6/D8).** When a run genuinely cannot finish (a permanently-unresolvable bead, an obsolete spec, a user decision to stop), `praxis verify --execution <id> --abandon --reason <why>` is the legal terminal: it archives every not-yet-resolved bead with `metadata.disposition: 'abandoned'` (via the `isResolvedForClose` predicate — never an inlined state literal), mints a terminal reference bead carrying `abandon_reason` + the disposition, patches the row `status: abandoned` + `abandonedAt`/`abandonReason`, and clears `parked`. Idempotent on an already-abandoned row; refuses a `completed` row.

**Close-blocked divergence (D12 — JSON vs bare).** When `verify --execution` (without `--abandon`) finds the run cannot close (an unresolved decision / unsatisfied bead), the response shape DIVERGES by mode so auto-drive gets a legal terminal while humans get a hard error:

- **JSON mode** (`PRAXIS_AGENT_INVOCATION=1` / `--json`) returns `{data:{closeable:false, unresolved:[{short_id, factory_id, state, type, classification, hint}], hint}, next_action:null}` at **exit 0** — auto-drive needs a legal turn-end, and the `unresolved` block (with the abandon hint) tells the agent how to proceed. This is the `data.unresolved` shape §6.5 names.
- **BARE mode** (no `--json`, env unset) keeps the pre-0.11.0 `CLIError` throw at **exit ≠ 0**, byte-for-byte — humans and shell scripts want a hard error, not a quiet success.

**Convergence with the runtime-exhaustion safety net.** Three wait/blocked semantics share `next_action: null` but are distinct — the agent disambiguates on `data`:

| Semantics | Frontier class | Row state | `next_action` / `data` | Resolution |
|---|---|---|---|---|
| **Healthy park** | `parked` (human/timer/event) | `in_flight`, `parked` set | `null` + `data.parked` (has `kind`) | resumes on wait satisfaction (§10.5 triggers) — no human fix needed |
| **§10.9 failure route** | `needs_user` | `in_flight`, `parked` set (kind-less or kind=human) | `null` + `data.parked` (`assignee: user`, `failure_reason`) | human fixes the bead, re-runs `update` |
| **Runtime safety net (true wedge)** | nothing ready, nothing legally parkable, not closeable | `in_flight` | `null` + `data.parked` with a **kind-LESS** blocker listing + abandon hint | human resolves or `verify --execution --abandon` |

The first is a normal suspension; the second is the always-on per-bead failure net (`waiting_for + assignee=user`); the third is the run-level wedge that the abandon exit closes honestly instead of leaving a zombie `in_flight` row.
